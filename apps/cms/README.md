# SignForge CMS

The web app people use to manage their screens: TanStack Start (React 19) with Tailwind and shadcn/ui, running as a Cloudflare Worker (`signforge-cms`). It holds no data of its own. Everything comes from the API Worker (`apps/api`).

## How it reaches the API

The CMS and the API are two Workers on one hostname, so the session cookie is same-origin (docs/backend-plan.md#layout).

- **The browser** calls `/api/...` on the page's own origin: Better Auth's client for sign-in and organizations. In a deployed environment, the API Worker's route takes `<host>/api/*` and the CMS takes the rest. If a request for `/api/*` reaches the CMS anyway, as it always does locally, `src/routes/api/$.ts` hands it to the API over the service binding unchanged. `/v1/device/*` is the same (`src/routes/v1/device/$.ts`), for the test screen.
- **The test screen** (M3-41) is the player build (`pnpm build:player`, in `dist/player`) at `/test-screen/`: `vite dev` serves it from there and `vite build` copies it into the site's assets (the `playerBuild` plugin in `vite.config.ts`, which serves the same build at `/player/` for the spot editor's stage). It talks to the device API on this origin, never with the session cookie (docs/architecture.md, "Browser test screen").
- **Server code** (loaders, server functions) calls the API over the `API` service binding with the browser's cookies (`src/server/api.server.ts`). Any cookie the API sets on the way, such as Better Auth's refreshed cache cookie, is passed back to the browser.

**The tab's org** (#129). Every call names the org the tab shows, in the API's `TAB_ORG_HEADER` (`src/lib/tab-org.ts`): `callTool` and Better Auth's client add it in the browser, every server function called from the browser adds it (`src/start.ts`), and `callApi` passes it on. The API refuses a call whose org is no longer the session's, so a tab left on the old org after a switch in another tab says to reload instead of acting on the new org. The tab's own switch or create reloads its data naming the new org (`reloadAs`). A server render sends none: it shows the session's org. The refusal is a `Refusal` with code `org_changed` (`isOrgChanged`): a page that cannot load because of it shows the sentence and a Reload button (`src/components/route-error.tsx`, the router's default error page, which leaves every other error to TanStack's own), and Query never retries it.

The CMS changes data only through Better Auth's endpoints (sign-in, sign-out, create and switch organization; members, invitations and the org's name; your name and sessions) and the API's tool registry: pages call `POST /api/tools/:name` from the browser (`src/lib/tools.ts`), and loaders read through the same tools as the member (`src/server/screens.functions.ts`). Do not add data routes here.

**Tool calls** (#154) go through one module, `src/lib/tools.ts`: `callTool(name, input)` from the browser, and `tool(name, input)` and `all(name, rows)` from server functions (`src/server/tools.server.ts`), which read the answer the same way (`answer`). An output's type is the tool's own output schema's, by name, from `@signforge/tools/outputs`: a types-only import, so no tool code reaches the browser, and a page that reads what a tool does not return fails `pnpm typecheck`. The views in `src/lib` (`SpotView`, `ScreenView`, ...) are aliases of those types, never copies. Outputs are trusted, as the tools' tests check every output against its schema. Every refusal, on either side, is a `Refusal` with the code it was refused with (a tool's `ToolErrorCode`, the API's `org_changed` or `no_active_organization`, `network`), its sentence and its details; read it with `isStale`, `isConflict`, `isGone`, `isOrgChanged` and `toolMessage`. A server function's refusal reaches the browser as one, through a serialization adapter in `src/start.ts`. Only the command menu and `@signforge/media`'s uploads, which name tools as strings, use the untyped `callToolByName`.

## Look

The tokens in `src/styles.css` follow `docs/proposals/cms-ui.md`: neutral white, Geist and Geist Mono, field edges at 3:1, and screen states that each have a colour, a word and a shape (online filled, updating an arc, asleep a half circle, offline hollow and grey, needs-you a triangle and the only red). `test/tokens.test.ts` checks every text pair at 4.5:1 and every edge, ring, status glyph and chart mark at 3:1, in both themes; change a colour and run it.

## Run it locally

Two terminals, from the repo root:

```sh
# 1. The API, on http://localhost:8787. Sign-in codes are printed here.
pnpm --filter @signforge/api exec wrangler d1 migrations apply DB --local --env dev   # first time, and after new migrations
pnpm --filter @signforge/api dev

# 2. The CMS, on http://localhost:3000.
pnpm --filter @signforge/cms dev
```

The spot editor's stage frames the player build at `/player/index.html?source=preview`, served as the test screen is (below): run `pnpm build:player` first. It is built with `CMS_ORIGIN` unset, so it takes drafts from the origin serving it: this one (docs/architecture.md, Content sources). The editor needs templates: with `ADMIN_TOKEN` set in `apps/api/.dev.vars`, `SF_ADMIN_TOKEN=<it> pnpm seed:templates --api http://localhost:8787` adds the base ones.

A weather spot's place search (`find_places`) asks Open-Meteo's geocoding from the API. Data sources are polled by the API's one-minute Cron Trigger, which `wrangler dev` does not run on its own, so a spot's live values stay at "Waiting for the first check" locally until the poller runs (start the API with `--test-scheduled` and `GET /__scheduled?cron=*+*+*+*+*` runs it, as the e2e does). A menu board's items can come from a CSV or JSON link (issue #84): the Source section reads the link at once (`read_table`, from the API), shows its first rows, adds it as a `csv` or `json-table` source and binds the items with a mapping guessed from the column names, which the person adjusts (a column per item property, which rows, what order); the stage plays what was read until the first poll. "Type the items instead" unbinds them; the link stays as the org's source.

Open http://localhost:3000, enter any email address, and read the 6-digit code in the API's terminal (`[email] to you@example.com: Your SignForge code: 123456`). The sign-in page says this in dev. GitHub sign-in appears only when `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are set in `apps/api/.dev.vars`.

The CMS's `API` binding finds the API's `wrangler dev` through Wrangler's local dev registry, so either can start first. Both must use the same registry: if you set `CLOUDFLARE_DEV_REGISTRY_PATH` for one, set it for both. Nothing is proxied by port.

## Command menu

⌘K or Ctrl+K on any signed-in page, or "Search and actions" in the sidebar, opens it. It lists:

- **Every section of the sidebar** (`SECTIONS` in `src/lib/sections.ts`). A new page gets its "Go to" entry by being added there, with nothing to change in the menu.
- **Switch organization…**, only for a member of two or more orgs, which lists them in the menu, and **Create organization…**, which opens the same dialog as the account menu (`orgCommands`, #182). The sidebar shows the active org's name under the logo as plain text, a menu only when there is another org to switch to.
- **Every tool the member's role allows**, read with the shell from `GET /api/tools` (the registry's `describeTools`, the list an agent gets), named from the first sentence of the tool's description. A tool with a required input opens a form built from its input's JSON Schema (text, number, choice, checkbox, or JSON for lists and objects; an idempotency key is filled in); one without runs at once. A field named like a route param (`screenId` on a screen's page) starts with the page's value. Results and refusals are toasts (`sonner`); a refusal keeps the form open.

It opens with no motion (docs/research/cms-ux.md). State is the `commandMenu` slice (`src/state/command-menu.ts`).

## React rules

`eslint.config.js` adds what Biome cannot check. Biome still formats and lints the whole repo.

- **No `useState`, and no `useEffect`, `useLayoutEffect` or `useInsertionEffect`.** Effects and state scattered across components are where UI bugs hide: a value copied into state goes stale, and an effect that syncs it runs at the wrong time or not at all. Instead:
  - App and flow state goes in the app store (next section). `useReducer` is allowed only for state that belongs to one component and never leaves it, as a small typed reducer.
  - Work caused by an event goes in the event handler or a store action.
  - DOM work such as focus goes in a ref callback. Make it a stable function (see `focusOnMount` in `routes/sign-in.tsx`): an inline one runs on every render.
  - A value that follows from props, loader data or the store is derived during render, not kept in sync.
  - Outside state, such as storage or a media query, is read with `useSyncExternalStore` or kept in the store, which subscribes once (see `connectUi` in `state/ui.ts`).
  - The ban needs named imports (`import { useId } from 'react'`); a namespace import of React is reported too.
- **Controls wait for their own part of the page to hydrate.** A route's component hydrates after the root sets `body[data-hydrated]`. A controlled field changed in between is set back by React when it takes the field over, and the old value is saved. So an editor's fields and actions, a settings control that saves or shows at once, and a filter or search that navigates (the audit log's, Assets', Screens') or a form held in the store (pairing a screen) sit in `EditorFields` (`components/editor.tsx`), a fieldset disabled until it has hydrated. `EditorHeader` puts its actions in one. Each page's e2e spec checks the server's HTML (`disabledOnServer` in `e2e/helpers.ts`). A search that can be an email or a name stays out of every URL: the audit log's lives in the store, its read is a POST server function, and only its non-personal filters (who as a kind or member id, what, target, when) go in the page's URL. A form that holds a URL, an email or a secret also posts (`method="post"`, with `server: { handlers: backToPage }` on its route, `src/server/form-post.server.ts`), so a browser's own submit, without script, sends it in the body and gets the page again by GET: a value never reaches the URL, history, a Referer or the request logs.
- **A control is not disabled while an action runs.** Chromium moves focus to the page when the focused control becomes disabled, so a keyboard user who changes a role or presses Resend would start again from the top. While one action runs, the store ignores another, and its controls say so with `aria-disabled` and a dimmed look. `disabled` stays for people who cannot edit, and for hydration. Every way out of an action releases it: an answer, a refusal, a request with no answer, a failed reload, the browser leaving.
  - In Settings, `run` in `state/settings.ts` runs one action at a time per page and org (`SettingsScope`), so an action waiting on the server holds up only its own page. It holds an action until the page's loaders have finished (`router.invalidate({ sync: true })`), so a role select shows its new role, and takes no other change, until Members has read the members again.
  - The settings forms (General, Screens & groups, the alert rules, Who publishes) are controlled. Their edits are kept in the store, by org, with the settings version the first edit was made on. A field shows its edit, else what the page read, so a reload refreshes every field not edited. A save sends only the edited fields, with that version: a change made since is refused and offered a reload, never overwritten. The forms share one version, so a save also moves the org's other edits still on the version it started from to the one it made, and Reload drops only the refused form's edits. Edits typed while a save runs are kept, and are kept on leaving the page, marked Unsaved changes by the Save button; Save with nothing edited says so.
  - Edits, running actions, errors and confirmations belong to their org. A switch drops the old org's edits and confirmations, and a late answer for an org the tab has left is not announced or reloaded (`orgOnScreen` in `lib/live.ts`).
  - A removal once sent cannot be called back. The webhook's Keep it waits for the answer; the member dialog can be closed (Close, Escape), says it is waiting, and its row shows Removing and how it went.
  - In brand kits, a kit action, a save and a new kit run one at a time (`kitActionRunning` in `state/brand-kits.ts`). A new kit on its way survives its dialog closing, and a create or copy that finishes after the member has moved on does not navigate.
- **No `create` from `zustand`.** It makes one store for the whole server, shared between requests. Use `useAppStore`.
- **React hooks rules** (`eslint-plugin-react-hooks`, recommended).
- **Slop rules** (`eslint-plugin-slop`, every rule, whole files): no em dashes, no inflated words, non-JSDoc comments of 50 words at most, `/** */` on exported things, no trivial wrappers or type aliases.
- **Typed rules** (typescript-eslint, with type information): no floating or misused promises, no condition the types say is always true or false (a fallback for a field that is required), no assertion that changes nothing, every case of a union switch and no needless `default`, only `Error`s thrown (TanStack's `redirect()` and `notFound()` excepted), and no deprecated APIs (React's `FormEvent`: use `SubmitEvent`). They add about 2 s to the lint.
- **Errors keep their cause.** A new error thrown inside a `catch` passes the caught one as `{ cause }` (`preserve-caught-error`; Biome's `useErrorCause` does the same for the rest of the repo).

If a rule must be broken, use `// eslint-disable-next-line <rule> -- <why>`: a disable without a reason, or one that no longer silences anything, is an error. There are none today.

typescript-eslint, which parses TypeScript for ESLint, cannot load TypeScript 7. So this package's `typescript` devDependency is an alias for `@typescript/typescript6`, the TypeScript 6 API, as the TypeScript 7 release notes recommend. `tsc` still runs TypeScript 7, from the repo root.

## State

Where each kind of state lives:

- **Server data** comes from the API through the tools. The shell, screen detail and assets pages read it in route loaders. The Screens list, the spot and playlist pages and Integrations read it through TanStack Query (docs/research/cms-data-layer.md, Decision): `src/queries/` holds each read as `queryOptions`, keyed `['org', orgId, ...]` so another org's rows never show after a switch, with a server function behind each fetch. A loader fills the cache (`queryClient.query(...)`), the component reads it with `useSuspenseQuery`, and the cache is made per request and streamed to the browser (`setupRouterSsrQueryIntegration` in `src/router.tsx`). Server data is never copied into the store; a store action that changes it writes the tool's answer into the cache (`setQueryData`) or invalidates the keys it touched. The Screens list polls `list_screen_status` every 15 seconds while the tab is visible and lays what each screen is doing over the list it loaded (`src/queries/screens.ts`), so a screen that stops syncing turns unreachable on an open page; it reads the full list again (settings, what each should be showing) only when the poll sees a screen, a publish or a change of state (a screen waking, say) that the list does not have, and on every load (`src/lib/fleet-status.ts`). Settings, Screens & groups polls the same tool to keep retired screens out of the Groups list (`screenRosterQuery`), and reads the full list again only when a screen comes or goes. A poll fails when two tries in a row do; while it fails, the page says its status is not current and when SignForge last answered, until the next good poll (Query's `errorUpdatedAt` later than its `dataUpdatedAt`; `isError` goes back to pending on each retry of a poll that has never succeeded). A read whose session has ended throws a redirect to sign-in that carries the page to come back to (`tool` in `src/server/tools.server.ts`: the page load's own URL, or a server function call's `Referer`), so it keeps the way back whether it or the shell's redirect wins; a call made from sign-in itself (a read of the page before, ending once the address is sign-in's) keeps sign-in's own way back instead of nesting it (`signInBack` in `src/lib/paths.ts`). A loader follows it as any redirect; a query that gets it (the poll, or a refetch when the tab is shown again) is followed once by the router's Query integration (`setupRouterSsrQueryIntegration`, which handles redirects by default), at once: Query retries a failed read (three times in the browser, as by default, loaders' reads too; once for the Screens and Integrations polls) but never a redirect (`retryUnlessRedirect` in `src/queries/retry.ts`). The server functions over tool outputs set `strict: { output: false }`: tool outputs are JSON, but template data is typed `unknown`, which Start's serialization check cannot prove.
- **Anything a link should carry** (list view, filters, search, selected tab) lives in the route's typed search params (`validateSearch`). The URL is state too.
- **The Audit log** reads `list_audit_log` as an infinite query (`src/queries/audit.ts`), keyed by org, the filters in the URL and the search in the store (`audit.query`, never in a URL: it can be an email or a name). `getAuditPage` is a POST server function, so neither reaches a request URL. The loader reads the first unsearched page, Load older the next. Export CSV pages the same tool from the browser, 200 entries a call, into one file of at most 10,000 rows (`exportAuditLog` in `src/state/audit.ts`), after a byte order mark so Excel reads UTF-8, members by name; a cell a spreadsheet would run as a formula gets a leading `'`. A page refused part-way (another org's cursor, after the member switched org in another tab) leaves no file, and Load older shows the refusal with a Reload. The route's `validateSearch` returns every key, undefined when dropped, because the router lays a route's search over the raw params; `q` is always undefined, so an old link's `?q=` is dropped. Inputs come as the API recorded them, redacted, so the page and the file never hold a secret. `test/registry/audit.test.ts` fails when a tool that changes something has no words in `ACTIONS` (`src/lib/audit.ts`).
- **UI and in-progress state** (the drawer, the theme, the sign-in steps, form drafts, later the spot editor's draft) lives in the app store, `src/state/`.

The store is Zustand, built with `createStore` from `zustand/vanilla`. `getRouter()` in `src/router.tsx` makes one store per router, which is one per request on the server and one per page in the browser, and its `Wrap` provides it. Components read it with `useAppStore(selector)`, select one value or action at a time (a selector that builds a new object re-renders forever), and call actions. They hold no state of their own.

Keeping it in one place means every change to the UI's state is in `src/state/`, as named actions, where a person or an agent can read them all.

To add a slice:

1. Make `src/state/<area>.ts` with its state under one key (`ui`, `signIn`, `orgs`, `screens`) and its actions, typed as `SliceCreator<YourSlice>`.
2. Name actions as verbs on the domain (`openDrawer`, `startSignIn`, `createOrg`) and write each transition inside them with `set((s) => ...)`. Do not add a generic `patch` or `setField` action: that is `useState` under another name.
3. Actions that call the API use the helpers in `src/lib/`, and the router and Query client from the store's deps (`router.invalidate()` after a change to loader data; `queryClient.setQueryData` or `invalidateQueries` after a change to Query data). An editor's edit of a versioned row is a versioned draft (`src/state/versioned-draft.ts`, GLOSSARY.md): the slice keeps the drafts in its state and gives the module the save call, and the module sends the version the edit started from as `ifVersion` (`packages/tools` README, Conditional updates), runs a record's saves one at a time (a save asked for meanwhile is one follow-up, and awaiting it waits for both), keeps the edit and offers Reload on a conflict, ignores an answer for an org the tab has left, and keeps a create's idempotency key until it is answered. A saved draft is shown and built on only while the record the page holds is still at the version it saved; once someone else's save has been read, the page shows the record and the next edit starts from it (`shown`, which every editor page uses for what it shows). A save belongs to the draft it was asked for, so a dialog closed and opened again mid-save saves on its own. A refusal is shown as it is; only a store that says so (the playlist editor) treats a `not_found` about the record itself as gone. Autosave is its debounce on top. A change to a list uses the tool's add and remove forms, never a replace built from what the page loaded; an ordered list a tool takes whole, a playlist's spots, is sent with the `ifVersion` it was read at, so a replace from an old read is refused.
4. Add the slice to `AppState` and `createAppStore` in `src/state/store.ts`. If it must start from browser state, set that in a browser-only hook like `connectUi`, which changes the current state but not the initial one, so hydration still matches the server.

## Deploying

Nothing is deployed yet. `wrangler.jsonc` has no default environment, as apps/api has none: `dev` is local only, and `demo` and `prod` each bind `API` to that environment's API Worker. Build with `CLOUDFLARE_ENV=<env>`; the build writes the deployable config for that environment. Routes are added when hostnames exist (M3-24): the API Worker gets `<host>/api/*` (and `/v1/*`, `/health`), this Worker gets `<host>/*`.
