# SignForge template spec

Version 1. This is what a template author, human or agent, builds against and what a reviewer checks. The types and limits here are defined in code in `packages/contract/src/shapes.ts`; if the two disagree, the code is right.

Working examples are in `templates/`: `cstore-promo` (price promotion), `photo-promo` (full-screen photo), `weather` (live data, canvas-drawn rain and snow, and the sun and moon placed from the feed's sunrise and sunset by `now()`), `clock` (live time), `agenda` (calendar feed, list field), `news` (an RSS feed's stories with their photos and summaries: the lead's text in a fixed column beside its photo, rotating through the latest stories, and a strip marking the one on screen, in the four looks of the look kit; see [News](#news)), `menu-board` (a list typed by people or filled from a CSV or JSON link), `room-status` (a calendar feed read against `now()`: free or busy, until when and the rest of the day, in the four looks of the look kit, with toggles), `info-frame` (a photo with a caption, framed by a clock, the weather and a news crawl from two live sources, the rail and the crawl placed by fields; see [Info frame](#info-frame)), `alert` (a takeover in fixed severity colours, with a QR code; see [Alert](#alert)), `announcement` (company news in the look kit's four looks, with toggles, facts and a QR code) and `countdown` (the days to go to a `datetime`, or the days since one with a record to beat, worked out from `now()` in the screen's zone and ticking once a second at most, in the four looks of the look kit, with toggles; a countdown has no start, so its progress is drawn over its last `progressDays` (14 by default) and shown once the days to go fit inside them, so it only ever moves forward; once its target has passed it shows the done text, or zeros, even in the hour the clocks repeat; in portrait it holds its ambient motion still, which took a fade over 1% on the Pi).

## What a template is

A folder with four files:

| File | Purpose |
| --- | --- |
| `template.json` | The manifest: identity, fields, duration range, orientations. |
| `index.html` | Markup. Must reference `style.css` and `main.ts` exactly as the example does. |
| `style.css` | Layout and animation. |
| `main.ts` | Calls `defineTemplate()` from `@signforge/template-sdk`. |

The build (`sf build`) bundles these into one self-contained HTML file with the script, styles and fonts inlined. That single file is what ships to screens. A template in `templates/` is also a workspace package, with its browser tests in `test/browser.test.ts` (see the update lifecycle, below); the build reads only the four files.

## Manifest

```json
{
  "id": "cstore-promo",
  "version": "1.1.0",
  "name": "C-Store Promo",
  "fields": {
    "price": { "type": "text", "label": "Price", "default": "4", "maxLength": 5 },
    "imageLeft": { "type": "image", "label": "Left product" }
  },
  "duration": { "defaultMs": 8000, "minMs": 4000, "maxMs": 60000 },
  "orientations": ["landscape", "portrait"],
  "uses": [],
  "background": "#06122b"
}
```

- `id`: lowercase letters, digits and dashes.
- `version`: semver. A published version never changes; any edit is a new version.
- `fields`: what the CMS form shows. Types are `text`, `number`, `boolean`, `color`, `select`, `url`, `date`, `datetime`, `image` and `list`. A `list` is repeating rows (menu items, events, headlines): it declares an `item` with its own scalar fields and optional `image` fields, plus an optional `maxItems`. A list row's `image` property holds an optional `NewsImage` (`{ file, thumb }`, stored SHA-256 hashes, never a URL); a table binding cannot map a column onto it, and a template declaring an `image` property in `list.item` needs manifest schema 8 (#196), so players before #196 (schemas 6 and 7) are told to reload. A `number` may set `min`, `max` and `step` (counted from `min`, or from 0); a `text` may set `maxLength`, and `maxMarks`, the most combining marks (accents, vowel signs, tone marks) on any one character, a grapheme cluster (so a joiner between runs of them hides nothing): Zalgo text stacks dozens, whose ink stands far past its line, over whatever is near. Written languages stack a few (Vietnamese two, Thai three), so it is a field's choice, not a rule for all text. A `url` holds a web address people type, such as a QR code's: an `https:` URL of well-formed text, at most `MAX_URL_BYTES` (2,048) bytes of UTF-8 so a QR code can always carry it, or `''` for none (the template then leaves the QR code out); it may set `maxLength` too, and `maxBytes`, a bound on its UTF-8 bytes, which is what a QR code holds: some characters use more than one byte, so 200 characters of Japanese are 560 bytes and a far denser code than 200 of ASCII. A template with a `url` field needs manifest schema 5 or later: a player before #191 plays schemas 3 and 4 and refuses such a template, so the server tells it to reload (`canPlay` in the contract's `playable.ts`, which sync calls), into a player that plays 4 and 5. A `date` is a calendar day, `YYYY-MM-DD`; a `datetime` is a wall time, `YYYY-MM-DDTHH:mm`, with no zone or offset, which the template reads in the screen's time zone: "Friday 18:00" means 18:00 where each screen is, as a person means it, whichever zone the editor is in (an instant would tie the spot to one zone, and a screen elsewhere would count to another hour). Both may set `min` and `max`, of their own kind, and hold a year from 1900 on (typing "26" into a picker's year gives 0026). The CMS shows the browser's date or date-and-time picker. A new spot starts at `min`; with no default or `min`, it starts empty, as an image field starts with no image: the spot is saved, the editor says the field has no date yet, and a publish holds the spot back, saying so, until one is picked (`draftCheck` in `@signforge/compiler/draft`). A list row's date does the same. A bound date or datetime needs its fallback like any bound field, so it is not saved until it has one. A screen never gets an empty date. A template with either needs manifest schema 6: a player before #192 plays schemas 4 and 5 and refuses it, so the server tells it to reload, into a player that plays 5 and 6. Every non-image field needs a `default` or the spot must supply a value. A text or list field's default is the preview's sample copy, the words its thumbnail shows. A spot made from New spot in the CMS starts with it (#360, `save_spot`'s `sample`). The server records those fields on the draft (`sampleFields`) until a saved edit changes each, the editor marks them, and a publish that would put any live is refused (`sample_text`) until a person chooses to publish anyway; a spot the agent fills, and every field bound to live data, starts empty instead, so the template must still draw an empty one well. A bound field's fallback is the spot's own value, empty until someone types one. These limits are enforced, on the template's own defaults and on every spot's data, by the contract's `validateTemplateManifest` and `validateSpotData`.
- `portraitBox` (optional, on a top-level `image` field): the largest box the template draws that image in on a portrait screen, in CSS px at 1080x1920, at any moment of the spot (transforms such as a push-in included) and with any toggle. Each asset has a landscape and a portrait rendition, the smallest that covers each screen; a 16:9 photo's portrait one is 3413x1920, 3.2 times the pixels of its landscape one, which a photo in a frame never needs. With a `portraitBox`, a portrait screen gets the landscape rendition when it has fewer pixels and covers the box drawn at most `PORTRAIT_BOX_UPSCALE` (1.25) times its size, as News's photos are (#224). Leave it out for a photo that fills the screen or most of it (Photo promo, Info frame): the portrait rendition is what they need. A browser test holds each box to what is drawn (`largestImageBox` in `@signforge/template-test`, over every look and toggle): Announcement 1.1.2's photo is drawn up to 1113x1746 (`{ "w": 1120, "h": 1750 }`: Night's photo row takes what the copy leaves, most with every other element off and no headline), so a 16:9 or 3:2 photo keeps its portrait rendition there and a 4:3 one gets its landscape one (1920x1440, not 2560x1920); C-Store Promo 1.3.1's products are drawn up to 285x796 (`{ "w": 290, "h": 800 }`). The test plays every look with everything on, with the template's defaults, and with the photo alone under a long, a short and no headline.
- `duration`: a spot may run for any length inside `minMs` to `maxMs`.
- `orientations`: `landscape`, `portrait` or both.
- `uses`: list `canvas`, `webgl` or `audio` if the template needs them.
- `background`: the colour shown around the template when it is letterboxed on an orientation it does not support.
- `live` (optional): the fields a data source fills, or several data sources by name. See [Live data](#live-data).
- `protocol` is added by the build: the frame protocol of the SDK it bundled. A rebuilt template speaks the current protocol (2), so it needs a new version; published bundles keep the protocol they were built with, and the player speaks every protocol in `SUPPORTED_PROTOCOLS` (1 and 2).

## Lifecycle

The player and the template talk only through messages. The SDK handles all of it.

1. The template loads and reports `loaded`.
2. The player sends `init` with the spot's data, its image files, the duration of this play, the orientation, the viewport size, the screen's time zone and locale, and (protocol 2) the screen's clock and, when the screen has a brand kit, its theme.
3. The template's document is hidden from load until this first `init`, and until its frame has its size. A new frame starts at 0x0, and what the browser tiles before the size arrives keeps the smallest tiles: on the Pi a full-screen layer then took about a second to raster. Nothing a template does in `prepare` sees the difference.
4. The SDK fills in the data, waits for fonts and images to decode and for the result to be painted, pauses every animation, and reports `ready`.
5. When the spot goes on screen the player sends `play`. Every animation restarts from zero.
6. The player removes the template when the spot's duration is up. The template is not asked.

A template that has not reported `ready` within 2 seconds is skipped.

**A new size for a template on screen** (a rotation or an HDMI mode change without a reload, #457). The player gives the frame the new size and, as for new data below, sends `reset` and an `init` with the new orientation and viewport, then `play` if the spot was playing (its animations restart). A protocol-1 bundle is loaded again instead. So a template fits its copy in `prepare`, from `ctx.viewport`, and needs no resize handler of its own. The spot loading underneath is fitted the same way, and is not played until it is. Resizes that arrive while one of these is under way are coalesced into one more, so a burst costs at most two inits, and the last has the final size; one that leaves the size as it was costs none. A template that fails to become ready again within 2 seconds is removed and its spot skipped: on screen, the next spot cuts in as soon as it is ready (on a one-spot playlist, the same spot loaded afresh at the new size); underneath, it is never shown.

**New data for a template on screen** (the editor's preview, protocol 2). The player sends `reset`: the SDK calls `stop`, cancels animations, releases the image URLs, restores the document exactly as it loaded, and reports `loaded` again. The usual `init`, `ready` and `play` follow. An `init` that arrives without a `reset` is handled the same way. So `prepare` always starts from the markup in `index.html`, and a list is never built twice. What this asks of a template:
- Look elements up inside the hooks, not once at the top of `main.ts`: a reset replaces them.
- Clear any state kept outside the DOM (a timer, a module variable) in `stop`.
- After each `await` in `prepare`, stop if new data came meanwhile: the SDK has restored the document and inits again, and a write from the old prepare to the root (`<html>`, the same element after a restore) or to anything it looks up in `document` lands on the new document. Note `document.body` before the wait and throw if it is another one after it; the SDK drops a superseded prepare's error (`templates/alert`, `templates/photo-promo`). A browser test holds the first prepare at its wait with a promise, sends the new data and lets it go (`packages/template-looks/test/looks.test.ts`).

Each template's browser tests check it (`templates/<id>/test/browser.test.ts`, its package's `test` task, on the harness in `packages/template-test`): new data after the first `init` must leave the same document as a fresh load. `useTemplate`, which every template's tests start with, takes the two sets of data and runs that check. A protocol-1 bundle has no `reset`; the player reloads its frame instead. A new template gets its own `test/browser.test.ts`, and goes into the devDependencies of `packages/cli`, `apps/api` and `apps/template-check`, whose tests build every template, so CI reruns them when it changes; `scripts/check-template-deps.sh` fails until it does both ([`ci.md`](ci.md#what-affected-means)).

## What the SDK gives you

- `data-sf="field"` on an element sets its text from that field.
- `data-sf-src="field"` on an `<img>` sets its source from that image field.
- `bindRow(el, ctx, field, index)`, `rowImage(ctx, field, index, prop, variant?)` and `rowAsset(field, index, prop, variant?)` from `@signforge/template-sdk/rows` (#196) fill `[data-sf]` text and `[data-sf-src]` images on dynamically built list rows (`data-sf-src="image"` for the lead copy `file`, `data-sf-src="image:thumb"` for the thumbnail `thumb`). The player puts each held row image into `init.assets` under `rowAsset(...)` and strips any row's image whose blob did not arrive; `bindRow` hides an `<img>` with no URL and removes its `src`, and reads only the row's own image, never a top-level asset of the same name, so a missing blob plays as a story with no image, never an empty frame. Its own entry point (alongside `@signforge/contract/row-asset`) so templates without list-row images keep their bundles byte for byte.
- `--sf-duration` on the root element is the length of this play. Use it to time the outro: `animation-delay: calc(var(--sf-duration) - 0.7s)`.
- `data-orientation="landscape|portrait"` on the root element. Use it for layout, not a media query, because a letterboxed template is not the shape of the screen.
- `defineTemplate({ prepare, play })` hooks for anything markup cannot do, such as building rows from a list or drawing to a canvas. `prepare` may be async; ready is reported after it resolves. A `stop` hook exists in the SDK but the player does not call it today: a template is simply removed.
- `formatter(ctx, options)` and `dayKey(ctx, date)` format dates and times in the screen's time zone and locale. Use them for anything shown: the device's own clock settings may not match the screen's location.
- `fitWords(text, fits)` shortens text to the whole words that fit, ending in "…": CSS `text-overflow` cuts after a space and shows "rain …". `fits` sets the candidate and checks for overflow (`packages/template-sdk/src/fit.test.ts`); it costs about log2(words) layouts, and only for text that overflows.
- `readableOn(fill, text)` from `@signforge/template-sdk/contrast` is `text` when it reads on `fill` (4.5:1), else black or white, whichever reads better; `readableOn(fill, text, { large: true })` asks 3:1, for large text (below). Use it for text on a fill the template does not choose: a colour field or a kit's colour, whose on-colour a kit may set by hand to a pair that fails (cstore-promo's badge, photo-promo's price tag). Use it the other way round for accent-coloured text, `readableOn(background, accent)`, measured against what the text really sits on: clock's greeting on `--bg` under its accent glow, menu-board's prices on their card, cstore-promo's promo line on the copy panel over the stage. Colours are `#rgb` or `#rrggbb`; a `color-mix` comes back from `getComputedStyle` as `color(srgb …)`, and a translucent card shows what is under it, so resolve the backdrop first with `painted(...layers)` from the same entry point, bottom first, a layer a colour or `[colour, opacity]` (menu-board: `painted(bg, getComputedStyle(card).backgroundColor)`). It reads a 1×1 canvas, so call it once per backdrop, not per row (agenda keeps one per kind of card). Text over a gradient is measured over both ends (agenda's stage, cstore-promo's). It is a separate entry point so that templates which do not use it keep their bundles byte for byte.
- `readableOver(pixels, text, { large, lightest })` from `@signforge/template-sdk/backdrop` is the same for a backdrop that is not one colour, text over a photo: given the RGBA pixels behind the text, it is `text` when it reads on every one, else black or white when one of them does, else undefined, and the text needs a fill of its own. With `lightest`, the pixels are an image's sample: each cell's darkest pixel in `pixels` and its lightest at the same place in `lightest`, and the text must read on every colour between the two.
  - **Read the sample, not the photo.** An image uploaded or built since #169 has a sample (`ManifestFile.sample` in the contract): its darkest and lightest pixel in each cell of `IMAGE_SAMPLE_CELL` (16) px, as a PNG of the darkest cells over the lightest. `init` carries it beside the image, as `ctx.assets[sampleAsset(field)]` (both from the same entry point). Drawing the photo into a canvas decodes it again on the main thread, whatever the size of the part read: 70 ms of a Pi's prepare for a 1080p photo. The sample is a few hundred times fewer pixels.
  - **Do not wait for the photo, and do not let it paint, while `prepare` runs.** Before `ready` the SDK awaits `img.decode()`, and the first frame's raster decodes the photo again; the two run one after the other, off the main thread, about 100 ms on a Pi. When a frame paints the loaded photo while `prepare` is still running, the raster's decode is scheduled first and the SDK's waits behind it, so `ready` waits for both: on the Pi that, not the canvas, was most of what #168 cost (`spike/pi-perf/RESULTS.md`, Photo samples). So photo-promo hides its photo (`visibility: hidden`) until `prepare` returns, and takes the photo's size from its sample, to the cell, rather than waiting for the photo to load. Calling `img.decode()` early does not help: each call decodes again.
  - **photo-promo's eyebrow** maps the text's box to the photo's pixels, wherever the push-in takes it during the spot, for every size within the cell the photo can be, and draws the sample's cells under that into a canvas, without smoothing, twice over: its darkest cells and its lightest. It paints the shade over each as the shade is at the box's top and at its bottom, and reads that once. A cell is a range, not an average: averaging is what kept the demo kit's orange at 2.88:1 in portrait over a 4K photo, measured one pixel per 4 px (#168). The two are chosen before the shade, so under it a third pixel of the cell can come out a little darker or lighter than both (a search of random pixels found up to 1.16 times the contrast under a dark kit's shade, 1.4 under a light or coloured one). Real photos rarely have such cells, and none of 252 cases measured on screen fell under 3:1. A sample that does not decode, or that the player does not hold yet, leaves the template to measure the photo.
  - **Without a sample** (an image uploaded before samples, or one with transparent pixels), or for a photo painted at more than twice its size, which is small and quick to decode and whose cells would each cover more than 32 px of screen, it waits for the photo to load and draws the photo itself, one pixel per pixel the screen paints it at, without awaiting `img.decode()` first, which decodes it a second time.
  - Where nothing reads, the eyebrow sits on a fill of the kit's background (a scrim) in `readableOn(bg, accent, { large: true })`. Its own entry point for the same reason as `contrast`: any edit to `contrast` renames symbols in every bundle that imports it.
- `qrSvg(text, label)` from `@signforge/template-sdk/qr` draws a `url` field's value as a QR code: an `<svg>` that fills its box, named `label` for screen readers. It is always dark modules on a white tile with the four-module quiet zone readers need, whatever the brand kit: a phone's reader needs dark on light and real contrast, so never recolour it. A longer address means more, smaller modules, so give the tile room and check on the Pi that a phone scans it from where people will stand. The Announcement sizes its tile for a scan from 2 m on a 55-inch 1080p panel: at least 30vmin (324 px at 1080p), which at about 0.63 mm a pixel is about 20 cm, a tenth of the distance, the usual rule for a phone's reader. On the 32-inch test monitor (700 mm wide, 0.36 mm a pixel) the same tile is about 12 cm, enough for about 1.2 m. The Announcement's `qrUrl` allows 100 characters, version 6 at error correction M (41 modules and the quiet zone), so about 6.6 px a module at 30vmin; its browser test decodes a 100-character address at the size drawn in every look. A longer limit needs a larger tile for the same module: Alert's `qrUrl` allows 213 bytes (`maxBytes`), the most QR version 10 holds at error correction M in any script (57 modules and the quiet zone), so it draws its tile at 40vmin, about 6.65 px a module, and its browser test decodes a 213-byte link, in ASCII and in Japanese, at the size drawn in every severity and orientation (#230). Error correction is M (a code still reads with 15% of it lost to glare). Place it in `prepare` (`box.replaceChildren(qrSvg(url, label))`) and leave the box out when the field is empty. Its own entry point, so templates that do not draw a QR code keep their bundles byte for byte; one that does carries the encoder's MIT notice (uqr) at the end of its script, as the licence requires.
- `wallTime(ctx, value)` from `@signforge/template-sdk/wall-time` is the instant a `datetime` field's wall time falls on in the screen's zone (`ctx.timezone`), or a `date` field's day starts on there. Work out what depends on it in `prepare`, from `now()`: a countdown's time to go is `wallTime(ctx, target).getTime() - now().getTime()`, and whether a `date` is today is `dayKey(ctx, now()) === day`. A wall time the clocks skip (02:30 the night they go forward) falls as much later as they jumped (03:30); one they repeat (01:30 the night they go back) is the first. Show the value with `formatter(ctx, …)` on that instant. Its own entry point, so templates that do not read dates keep their bundles byte for byte.
- `now()` is the screen's time: the device clock corrected from the server. Use it, never `new Date()` or `Date.now()`, for anything that depends on the time: a Pi has no battery-backed clock, and after a power cut its own clock can be days out. Something that follows the time without new data, like weather's sun and sky, works out its state in `prepare` from `now()`: the player prepares every play afresh, so it moves on from one play to the next. Round to the minute what should change at most once a minute.
- The screen's brand (protocol 2): see Brand below.

## Brand

When the screen has a brand kit, the player sends it in `init` as `theme`, and before `prepare` the SDK applies it:

- Colours and shape as custom properties on the root (`BRAND_CSS_VARS` in the contract): `--sf-primary`, `--sf-on-primary`, `--sf-accent`, `--sf-on-accent`, `--sf-bg`, `--sf-surface`, `--sf-text`, `--sf-muted`, and `--sf-radius` (square `0px`, soft `12px`, round `9999px`).
- Brand fonts: `--sf-font-display` and `--sf-font-body`, each set when the kit has that font and the template's `<style>` uses that variable. The SDK adds them as `@font-face` rules for `sf-brand-display` and `sf-brand-body` with `data:` URLs (as a template's own fonts arrive; nothing is fetched, and the no-network policy is unchanged) and loads them before `ready`, so the first frame draws with them. A family the template never uses is not loaded: on the Pi, unused faces still slowed the first paint of a large photo. Faces built from bytes (`new FontFace(name, buffer)`) were tried first and dropped: on the Pi about one prepare in three of a template over a 4K photo then took about a second to paint.
- The logo: `<img data-sf-src="$brand.logo">` gets the kit's logo, the on-light version when `--sf-bg` is light and the kit has one, else the on-dark one. It is also `ctx.assets['$brand.logo']`.

Cost on the Pi (`spike/pi-perf/RESULTS.md`, Brand fonts and Slow prepares): a kit costs a template that does not use the brand fonts nothing; drawing in them adds about 0 to 80 ms to a prepare, and with the shipped templates on the brand fonts (M3-25) every stress spot prepares within 500 ms except news loading under a playing video (550 ms, and 1.4 to 1.6 s when the video layer hides the frame underneath: RESULTS.md, Brand tokens and template polish). Measure a template on the Pi after moving it onto the brand fonts.

Write every brand value with a fallback, so the template still draws on a screen with no kit, where nothing is set: `color: var(--sf-text, #f8fafc)`, `font-family: var(--sf-font-display, Inter), sans-serif`, and give the logo `<img>` a `src` of its own (a `data:` URL) or hide it when it has none. Colours built on a token are fine: `color-mix(in srgb, var(--sf-accent, #22d3ee) 30%, transparent)`.

A colour field may default to a brand token, `"$brand.<colour>"` with one of the contract's `BRAND_COLORS` (`"$brand.accent"`). The server's compiler replaces it with the screen's brand colour at publish, so `data` only ever holds colours; a token naming no brand colour is a problem of the spot.

**Colour lint.** `sf build` and the server warn on a colour literal in a template's CSS (`style.css`, and `<style>` in `index.html`; `sf build` also reads the stylesheets `style.css` imports) that is not the fallback inside a `var()`: a hex colour, `rgb()`/`hsl()` and the like anywhere, and named colours (`white`) in colour properties. It is a warning: the version still builds and registers, and the warnings are kept on its check report. Each lint run reports the first 20, then one line with how many more there are; a colour function nested in another is part of the outer one's text, and a quoted colour or property longer than 80 characters is cut short with `…`. The shipped templates have none (`packages/cli/test/templates.test.ts` keeps it so). How they get there:

- Give each brand role its token: text `--sf-text`, secondary text `--sf-muted`, page `--sf-bg`, cards `--sf-surface`, filled shapes `--sf-primary` with `--sf-on-primary` text, highlights `--sf-accent`. The brand tools derive an on-colour that reads, but a kit may set one by hand that does not (they only warn), and a colour field's fill is whatever the spot sets: pass such pairs through `readableOn` in `prepare`. With no kit, `$brand.accent` is the default palette's amber (`#f59e0b`), on which white reads at 2.14:1. The accent is not a text colour for every background either: amber on a light kit's white is 2.15:1, so accent-coloured text goes through `readableOn` too. **Large text** is WCAG's: at least 24 px, or 18.66 px (14 pt) bold (700 and up), on the screen, and the screen is 1080p: the Pi 4 is the baseline device and is held at 1080p, so `1vmin` is 10.8 px, in portrait too. So text of `2.23vmin` and up, or `1.73vmin` bold, is large and needs 3:1; smaller text needs 4.5:1. Every shipped accent-coloured text is large (agenda's bold day labels at `2.2vmin` are the smallest, 23.8 px), and all pass `{ large: true }`, so a mid-tone brand accent such as green on white (3.30:1) stays the accent instead of turning black. At 3:1 there is no margin, so the backdrop must be the one the text is painted on: photo-promo's eyebrow, measured on the kit's background and not on the photo under it, kept the demo kit's orange at 1.99:1 over a white photo (#124). Text on a fill keeps 4.5:1. Asking 3:1 is a claim about the text's size: shrink the text below the line and drop the option. Each template's browser tests (`brandColourTests` from `@signforge/template-test`) measure both kinds under no kit, the demo kit, a kit with poor on-colours, a light kit, an accent just over 4.5:1 on the demo kit's background, green on white, blue on dark and an accent just over 3:1 on its background and a mid-tone background, photo-promo over a white, a black, a mid-grey and a black-and-white striped photo, broad and 1 px wide at the screen's scale, in landscape and portrait, with the threshold from each text's size at 1080p, and checks that a kit's accent is kept wherever it reads.
- Shades and shadows are the kit's background mixed with `transparent` (`color-mix(in srgb, var(--sf-bg, #000) 50%, transparent)`), and text over them the kit's text: the kit keeps that pair legible, so a light kit gets a light shade with dark text. A "light" theme option swaps the two (`templates/menu-board`).
- A colour that is not a brand role, such as a weather sky, is a mix of tokens whose two fallbacks are the same literal, so with no kit it is exactly that colour: `color-mix(in srgb, var(--sf-primary, #2f80ed) 75%, var(--sf-bg, #2f80ed))`.
- Canvas drawing is not linted; read a token with `getComputedStyle` to follow the kit (weather's rain and snow).

## Looks

A template that offers the four looks of the template set (#189), Pop, Poster, Night and Corporate, takes them from the look kit, `packages/template-looks`, instead of writing each one. One template per kind has a `look` field; the looks are not separate templates. A look sets type, shape, spacing and motion; the screen's brand kit sets the colours, and the look's palette from the concept canvas shows only on a screen with no kit. Its type and shape are the look's own: a brand kit's fonts (`--sf-font-*`) and `--sf-radius` are not used.

**Using it.**

1. Depend on `@signforge/template-looks` (`workspace:*`) and put `@import '@signforge/template-looks/looks.css';` first in `style.css`. `sf build` inlines it and its fonts like the rest of the template's CSS. An `@import` is refused only if one is left in the built bundle, where it would load at run time.
2. Declare the field: `"look": { "type": "select", "label": "Look", "options": ["pop", "poster", "night", "corporate"], "default": "pop" }` (`LOOKS`).
3. In `prepare`, first `await applyLook(ctx)` (from `@signforge/template-looks`). It sets `data-look` on the root, the toggles (below), the text colours (below), and waits for the look's fonts, so text measured in `prepare` (a crawl, `fitWords`) is in the look's own type. If new data arrives while it waits, the SDK restores the document and inits again, and `applyLook` rejects in the old prepare, so nothing after it touches the new document. A template needs no guard of its own unless it awaits something else after `applyLook`; then it checks `document.body` the same way (above).

`packages/template-looks/looks-test` is a template that uses every part of the kit, for the tests and the Pi. It is not in `templates/`, so it is never seeded. `templates/announcement` is the first shipped template on the kit. Two things it does that the next ones will want:

- **Nothing to show is off.** An element whose content is empty (no QR address, no logo in the kit, no facts, an empty line) is passed to `applyLook` as switched off, so the layout closes up around it as for a toggle.
- **Long copy steps down.** Its copy is a grid of `min-content` rows (an `auto` row lets an element with `overflow: hidden`, as a clamped one is, shrink below its text, and the next row overlaps it) around one flexible row. After `applyLook`, `main.ts` steps the headline's size (`--fit-headline`), then the body's and the facts' (`--fit-body`), down from the look's own until the headline fits its clamp, nothing falls below the copy and no two of its blocks overlap. It measures the layout's offsets, not painted boxes, which the intros' transforms move. The overlap check matters where a block spans the flexible row, as the QR code beside the body does: such a block is left out of the rows' sizing, so with no room left it rises over the headline rather than overflowing. Each step tried costs a style and layout pass, tens of milliseconds on a Pi, so the template's defaults are held to the first: a browser test plays them, with a photo and a QR code, at `--fit-headline` 1 in every look and orientation. Text at every field's `maxLength` ends in its clamp's ellipsis at the smallest step.

The kit's build test (all four looks within the bundle budget, the colour lint, the licence notice) is `packages/cli/test/looks.test.ts`: a template on the kit is a devDependency of the CLI, whose tests build every template, so the kit cannot depend on the CLI.

On the Pi, decoding a look's own faces costs under 10 ms. Carrying the other looks' faces costs more (`spike/pi-perf/RESULTS.md`, The look kit). The player reads every bundle before it frames it, about 30 ms more for this one than for a bundle with only Pop's faces. The first prepare after a page loads takes about 180 ms more. After that, prepares fall into a fast mode (about 300 ms in landscape for the test template) or a slow one (about 420 to 480 ms). The four-look bundle's runs land in the slow mode more often. A trace finds no thread doing more work for it, so the slow mode's cause is not known yet.

**Toggles.** Each element that can be switched off has a boolean field `show<Name>`, such as `showPhoto` or `showNowLine`. `applyLook` marks the root `data-<name>="on|off"` (`data-photo`, `data-now-line`) and removes every element marked `data-show="<name>"` when it is off. So the layout reflows around what is left: write it in flex or grid, which close up over a removed element, and key anything else off the root's marks. A photo that is switched off is never decoded, and needs no image: an image field whose `show<Name>` toggle is false (set or by default, and not bound to live data) is not required to publish (`validateSpotData`, #252). Type steps up into space an element leaves: each look has a `--lk-step` (Pop 1.18, Poster 1.2, Night 1.6, Corporate 1.15), and a template sets `:root[data-photo='off'] { --lk-scale: var(--lk-step); }` and sizes text as `calc(var(--lk-size-display) * var(--lk-scale))`. No template needs layout code in `main.ts` for a toggle.

**Motion.** D's (#news-design): an element arrives decelerating (`--lk-ease-in`, `cubic-bezier(0.05, 0.7, 0.1, 1)`) in 400 to 650 ms by role, 110 ms after the one before it in reading order, and leaves accelerating (`--lk-ease-out`, `cubic-bezier(0.3, 0, 0.8, 0.15)`) in 300 ms, on keyframes of its own, not its entrance reversed. It travels at most 1.5vmin in and 0.6vmin out, scales no further than 0.94 to 1.04, and never overshoots. Only `transform` and `opacity` move: no clip-path or mask reveal, which the Pi has not measured. Each look keeps its character through type, colour and corners, and through which of these motions each role takes:

| Class | Pop | Poster | Night | Corporate |
| --- | --- | --- | --- | --- |
| `lk-text`, 650 ms | rise | rise | rise | rise |
| `lk-fade`, 500 ms | fade | rise | rise | fade |
| `lk-badge`, 400 ms | press in from 0.94 | rise | slide in from the side | fade |
| `lk-photo`, 600 ms | slide in from the side | fade | settle from 1.03 | settle from 1.03 |
| `lk-draw`, 500 ms | a rule or bar drawn left to right | the same | the same | the same |
| `lk-drift`, ambient, landscape only | slow push-in to 1.04 over the play | the same | the same | the same |
| `lk-ping`, ambient | none | none | a live ping every 1.6 s | none |
| `lk-crawl` | steady crawl, `--lk-crawl-speed` vmin a second | the same | the same | the same |

- Each element with `lk-text`, `lk-fade`, `lk-badge`, `lk-photo` or `lk-draw` gets its look's intro, staggered by `lk-d1` to `lk-d8`. Its outro ends as the spot ends (`calc(var(--sf-duration) - var(--lk-out))`): text, fades and badges fade as they lift 0.6vmin (`lk-leave`), photos and rules fade (`lk-fade-out`).
- `motionContract(frame, durationMs, { loops, progress, exits })` in `@signforge/template-test` checks a play against all of this, and every template's browser tests run it in both orientations. It seeks each animation alone (CSS, transition or script, on an element or its `::before` or `::after`) through its whole active time, against its element at rest:
  - to rest from unseen, or from anywhere in the first 2 s (`INTRO_WINDOW_MS`), is an entrance;
  - from rest to unseen is an exit, which ends with the spot, or, inside `exits`, no later than that ancestor hides (a news story);
  - on an element `progress` selects (a bar or ring that shows time, or a marker that moves to the current item), progress: linear or the standard curve, along one axis (across, down, a turn, or a fill no larger than full size), one way each run, never back and forth, any reach, as often as it needs;
  - a loop is allowed only where `loops` selects (the crawl, a live ping, a clock's colon, Night's minute bar, the clock's 90 s drift against burn-in, drifting clouds and falling rain or snow, the alert's 0.5 Hz pulse). A loop that changes opacity cycles 3 times a second at most and swings opacity by 0.75 at most, so nothing flashes (WCAG 2.3.1);
  - half the play or more is ambient: any curve, 1.5vmin at most, and, for an element that covers the screen, a push-in up to 1.12 (photo-promo's photo);
  - a change in a millisecond or none is a cut (a story shown, a seam lit), not motion;
  - anything else is a move mid-play, which takes the standard curve (`cubic-bezier(0.2, 0, 0, 1)`) and travels 1.5vmin at most; a marker that moves further is progress.
  Each is read with its element's ancestors at rest, so neither their motion nor the wall clock moves what it reads.
  It fails on a clip-path or mask animation, a rotation outside progress, a finite animation that runs more than once, a value that turns back on its way (an overshoot), through any number of keyframes, a curve that changes between them, an element that rests on screen leaving it, and a keyframes name no stylesheet defines.
- Templates without the kit (agenda, alert, clock, cstore-promo, menu-board, photo-promo, weather) write the same motion into their own keyframes: `--d-in` and `--d-out` hold the two curves, and `--out` starts the 300 ms exit before `--sf-duration`.
- An ambient class goes on an element inside one that has an intro, so the outer element's outro takes it away.
- A crawl is a `.lk-crawl` strip filled in `prepare` and passed to `crawl(strip, ctx)`. It holds its content twice and slides by exactly one copy at the look's speed, however long the text is.
- Under `prefers-reduced-motion` nothing animates: every element shows its final frame, and a crawl is one line cut with an ellipsis.
- The Rules' cap holds: at most about 50 elements animating at once. Every element with a kit motion class also has `will-change: transform, opacity` for the whole spot, so each is a layer of its own, and a list with `lk-text` on each row reaches the cap quickly.
- `lk-drift` holds still in portrait. A photo drifting across a portrait screen's width was the largest part of what took the test template over 1% of frames dropped there (RESULTS.md, The look kit): 1.67 to 1.94% with it, 0.67 to 0.72% without. The kit turns it off in portrait (`:root[data-orientation='portrait'] .lk-drift`), and its `will-change` with it, so the held photo keeps no layer of its own, until a portrait template measures it under 1%. Landscape keeps it.

**Bundles.** `sf build` also runs the colour lint over every stylesheet `style.css` imports, the kit's included, and names each file from the template's directory. The server lints only the files it receives, the template's own. A template's bundle holds the kit, so an edit to `looks.css` or to the kit's script changes the bundle of every template that imports it. Each such template then needs a new version, as under Budgets.

## Alert

`templates/alert` is the takeover for emergencies and notices (#200): the severity in a band across the top, a headline, what to do, who issued it, when it ends, and a QR code for updates. It has one look of its own, not the four.

- **Its colours are the severity's, never the brand kit's.** Emergency is white on `#991b1b`, warning `#111827` on `#f59e0b`, advisory `#111827` on `#fde047`, notice white on `#1e3a8a`, each pair 7:1 or better, and the band is the pair the other way round. A kit's colours, fonts and radius are not used: a kit must not decide whether an evacuation notice reads, so a change to "use the brand colours" here is refused. `main.ts` sets them from one table, so the colour lint has nothing to warn on. The browser tests measure every severity as painted under no kit, the demo kit and a light kit, and check a kit changes nothing.
- **Its own type**: Space Grotesk for the band and headline, Inter for the rest, latin subsets with their OFL notice at the top of `style.css` (no Reserved Font Name).
- **The look kit's conventions, not the kit.** It does not import `looks.css`: the other looks' faces would add about 250 kB to the bundle and, on the Pi, about 100 ms to a prepare (Looks, Fonts), and an alert must start at once. It keeps the kit's toggle convention (`showQr`, `showIssuedBy` and `showEndsAt` as `data-qr`, `data-issued-by` and `data-ends-at` on the root, and what is off removed), and a QR code with no address is off too, as is an empty end. The end is a text field ("4:00 PM") until date and time fields land (#192); then it becomes a `datetime` read in the screen's zone, in a new major version. The grid closes up over what is gone, and with no QR code the type steps up 1.12. The QR code is 40vmin, sized to scan from 2 m on a 55-inch panel at its 213-byte limit (see `qrSvg`). Character limits cannot keep text in place, as the widest glyph can always be wider, so the body is three regions that nothing can grow or push (review of #448): the copy, the meta line (who issued it and when it ends), and the code with its caption under it in a box three lines high, of a fixed size. Text that does not fit its region scales down until it does, with no floor: the caption on its own (`--cap-fit`), the copy and the meta line together (`--fit`). `main.ts` measures the text against its region's box, within half a pixel, with the intros off: across, line by line (`Range.getClientRects`), and down, by its blocks' boxes, which are its line boxes (a line's own rect is its font's whole height, which a tall fallback font stands past by a pixel at some sizes, so a fit checked that way was not the same at every smaller scale). It searches the scale from an estimate made in the layout at full size (wrapped text needs height about as the square of the scale), then a step towards the answer, 1/64 when that probe's own layout puts the answer that close (two probes then bracket it) and 1/16 otherwise, then halves until it is within 1/64, the two scales' searches sharing each layout: three to six layouts as a rule, at most nine (eight probes always reach 1/64). A search of eight halvings for each region in turn took the widest copy's cold prepare to 590 ms on the Pi; this one keeps it under 500 ms (`spike/pi-perf/RESULTS.md`, Alert), with one accepted exception: with `﷽` in every field at its limit, the first prepare after a kiosk restart may take up to about 545 ms, well inside the 2 s ready timeout. Realistic copy fits at full size in one layout; every field at its limit in W's or Japanese scales to about 0.7, in `﷽` to about 0.29. Small text beats hidden or covered text in an emergency. Marks stacked above or below a character paint past its line though the line fits, so each text box clips its ink a little past its edges, less than half the gap to the next box (1.8vmin for the instructions and the meta line, 0.7vmin for the caption, whose gap to the code is 1.48vmin). The headline's line is tight (1.02), and Thai tone marks and Arabic and Hebrew points stand well past it, so it keeps room for them below in its own box (`padding-bottom: 0.25em`, which the fit counts) and clips 1.8vmin past that, and clips 6vmin out above, where only the body's padding is; and every text field refuses more than four marks on one character (`maxMarks: 4`). A browser test checks the code and the headline paint exactly as without such marks, and that headlines and copy in Vietnamese, Thai, Arabic and pointed Hebrew lose no ink to the clipping. A browser test fills every field with each of W, `﷽`, `ﷺ`, `⸻`, `⸺`, Japanese and Thai with stacked marks, in every severity and orientation: every line stays on screen and in its region, no region meets another, and the code reads back. The headline keeps its 40-character limit, at which the widest ordinary copy still fits at about 0.7. A spot on Alert 1.0.x keeps the 23vmin code until it is made again on 1.1.0 (`templates/alert/README.md`). 
- **Motion**: D's curves and limits. Emergency and warning arrive hard and quick (400 to 550 ms: the band drops 1.5vmin from above, the icon presses in from 0.94, the copy rises after it); advisory and notice fade in (650 ms). Each element leaves on its own 300 ms lift, ending at `--sf-duration`. Only an emergency pulses: the band's glow and its icon, once every 2 s (0.5 Hz), well under WCAG 2.3.1's three flashes a second. The browser tests read the duration of every animation that repeats. Under `prefers-reduced-motion` nothing moves.
- **As a takeover**: it plays through `start_takeover` like any spot, cutting in at once and ending on time offline. On a screen that does not trust its clock, a takeover that plays only Alert spots still plays while it has surely started and not surely ended, by the earliest the real time can be: the player's build or its last sync, plus the time the screen has run since. So a live alert is never held back, one scheduled for later does not show early, and one that is over stops, offline too (owner decision; `docs/architecture.md`, Clock).

## Info frame

`templates/info-frame` (#201) is the lobby screen: a photo with a caption (title, line and an optional price), a clock with the date, the weather now with a three-day forecast, the kit's logo and a crawl of headlines, in the four looks. The weather comes from an Open-Meteo source and the headlines from an RSS source, named `weather` and `headlines` (see [Several sources](#live-data)).

- **Layout fields.** `rail` puts the clock, the weather and the logo right of the photo, left of it, or nowhere; `ticker` puts the crawl along the bottom, the top, or nowhere. In portrait the rail is a band under the photo (`right`) or over it (`left`), the clock beside the weather. `main.ts` writes what is in force on the root as `data-rail` and `data-ticker`, and the CSS lays out from those and the toggles' marks.
- **Toggles**: `showClock`, `showWeather`, `showForecast`, `showCaption`, `showLogo`. What is empty is off too: no headlines is no crawl, a kit with no logo is no logo, a caption with no text and no price is no caption, and the forecast goes with the weather.
- **The canvas's rules.** A rail that would hold only the logo is dropped. With no rail, the clock and the weather are a chip on the photo's corner and the logo sits on the photo. The weather grows without the forecast, and the clock without the weather. The canvas's clock sizes fit "9:41" but not "10:00" in the rail, so each look's sizes are the largest at which the widest time fits; with the weather off, a landscape rail, too narrow for a bigger clock on one line, sets the hours over the minutes.
- **Text on cards.** No text sits on the photo itself: the caption, the chip and the logo each have a fill, and `main.ts` measures each card's inks through `readableOn` (an ink that is a mix of tokens is resolved first). Long copy steps the caption's title down (0.86, 0.74, 0.64 of its size) before the clamp's ellipsis; the clock and the temperature shrink only to fit their box.
- **Time.** The clock and the date are from `now()` in the screen's zone; the text is written only when it changes, from a timer that wakes on each second. Each live forecast day is named from its Open-Meteo timestamp (`daily.time.1`–`.3`) in the feed's own `timezone` (`weatherTimezone`), so a screen in another time zone or a snapshot cached across midnight keeps every temperature under its own weekday; static fallbacks (`0`) name the next three days from the screen's today.
- **Motion.** As the look kit's, with the rail sliding in from its own side. Looping motion (the colon's blink, Night's live ping and seconds bar) holds still in portrait, as Countdown's does (#218); the crawl runs. The photo stays unpainted until play, when its panel comes in from nothing (Announcement, #197). The crawl's speed is the look's times `crawlSpeed` (slow 0.7, normal 1, fast 1.4).
- **Bundle**: 403,207 bytes with all four looks.
- **On the Pi** (`spike/pi-perf/RESULTS.md`, Info frame), over a 4K photo with the crawl running: Poster, Night and Corporate landscape cuts drop 0.50 to 0.72% of frames (Poster landscape fade 0.44%, Poster portrait cut 0.50%, Night portrait cut 1.00%), with later landscape prepare medians of 410 to 454 ms (Pop 592 ms). Over budget (10/16 specs over 1% dropped, 58/80 prepares over 500 ms, 16/16 specs with worst frames over 50 ms): all four portrait fades (1.33 to 3.33%), Pop (2.33%, 1.27% playing) and Corporate (1.39%) portrait cuts, Pop (1.94%), Night (1.33%) and Corporate (1.11%) landscape fades, Pop landscape cut (1.44%); all 40 portrait prepares (568 to 994 ms, the portrait photo being 6.6 megapixels), all 8 landscape cold-load first prepares (698 to 855 ms), and 10 of 32 later landscape prepares (561 to 658 ms); and worst frames of 67 to 100 ms in every spec (while loading the next spot, plus one 67–83 ms play frame in each Pop portrait spec).

## News

`templates/news` 2.1 (design D, the owner's pick on #476) is the news screen: the lead story's source and age, headline and summary in a fixed column on the left, its photo beside it in the photo's own shape (above the text in portrait), turning through the latest stories, and a strip of those stories along the foot with a bar under the one on screen, in the four looks. Its stories come from an RSS source (`items`, `language`). Spots keep their version: one on 2.0.x keeps the card over the photo and the crawl, one on 1.4.x its text-only layout, until it is made again on 2.1.

- **Layout.** Header (the title and the time), lead, strip, inside the graphics-safe margin (5%). In landscape the text column is 44% of the width and the photo's area the rest; in portrait the photo's area is the lead's top half and the text hangs under it. The headline's left edge and first line are in the same place in every story, whatever its photo (a browser test).
- **Photos.** A story's photo is the feed's (`image`). It is drawn whole (`object-fit: contain`, its box its own shape), as large as its area holds and at most 1.25 times its size (some feeds send 700 px, which looks soft drawn larger), at the area's top and centred across it, never under text: a browser test draws 1920x1080, 1800x1800 (NYT), 1920x1280 (The Verge), 700x560 (The Guardian), 1080x1920, 2400x800 and 320x240 photos in every look and orientation. The size is the photo's own, read once it loads: the first story's from the decode the SDK makes before ready, each later one's when it loads in play, 3 seconds before its turn (feed photos carry no sample). A story without a photo, or whose blob did not arrive or will not decode, takes the width with its headline a step larger (`--nw-bare-step`), fitted again from its title; in portrait, where it has the whole lead, its headline is 1.6 times the size and its summary 1.3 times, up to five lines. Only the first story's photo is loaded in prepare: the SDK decodes every photo with a `src` before ready, and on the Pi four 1080p photos took a portrait prepare from about 460 to 600 ms.
- **Strip.** The listed stories (five in landscape, four in portrait) by their place, 1 to 5, each with its headline on one line in landscape and the number alone in portrait. The strip's text never moves; the bar under the story on screen is one transform animation the length of the play.
- **Rotation.** The lead turns every `rotationSeconds` (4 to 30, 8 by default) through the listed stories, each for an equal share of the play. Each story is a layer of its own (`.story`, over the one before it); `main.ts` sets its `--at` (its turn's start; the first's is 150 ms) and `--until` (its end). All of it is animation time, which the SDK starts at play, so a test seeks it (`currentTime`) rather than waiting.
- **Motion** (research for #476, Motion spec), the same in every look: at a story's change T, the old story's summary lifts 0.6vmin away from T - 400 ms, its source, age and headline from T - 350 ms, over 300 ms on the emphasized accelerate curve, so the old text has gone 50 ms before the new arrives, and its photo fades to the ground over the last 300 ms (a dip: two photos never cross-fade). From T, on the emphasized decelerate curve, the new photo fades in and settles from 1.03 over 600 ms, the source and age rise in at T + 100 ms (400 ms), the headline at T + 150 ms (650 ms, from 1.5vmin below) and the summary at T + 300 ms (500 ms). The bar moves from T - 150 ms over 600 ms on the standard curve, and a progress line along the foot sweeps once a story. The header fades in once (400 ms) and the strip rises in (500 ms from 100 ms); the whole spot fades out over its last 300 ms. Only transform and opacity move, text travels at most 1.5vmin, and nothing overshoots (a test samples a change every 10 ms in every look). Under `prefers-reduced-motion` the first story stands still and nothing moves.
- **Looks.** The kit's fonts and colours. Pop: Bricolage Grotesque, heavy and tight, with the look's tomato only as a fill (the bar and the progress line) over ink rules. Poster: Instrument Serif set large and solid, a heavy ink rule under the header, italic serif figures in the strip, and the accent (red, or a kit's) only for the age and the bar. Night (Ember) and Corporate as the kit gives them. Every look's headline starts at about 7vmin, read from about 6 m (research for #476); Night's wide face gets a sixth line in landscape so it holds that to about 80 characters.
- **Source.** Each story names the spot's credit (`source`) where one is set, and the feed's own source where not: a feed names itself as it likes ("NYT > Top Stories").
- **Toggles**: `showImages`, `showSummary`, `showList` (the strip), `showMeta` (source and age). What is empty is off too: one story is no strip, and a story with no summary or no source and age has neither.
- **Text** sits on the look's ground: no text on a photo. Long headlines step down (1, 0.86, 0.74, 0.64), then are cut to their lines on a word with "…" (on a character when there is no space to cut on), keeping every line they hold; a story's text never runs past its story's foot. A headline is never clamped or clipped, so no g, j, p, q or y loses its tail (a browser test turns every text box's clipping off and finds no pixel changed). Summaries are CSS line clamps (two lines, three in portrait), and the strip's titles a one-line ellipsis.
- **Bundle**: 385,598 bytes with all four looks.
- **On the Pi**: not measured for 2.1 (waived by the owner, 2026-11-26). 2.0's numbers are in `spike/pi-perf/RESULTS.md`, News 2.0.

## Live data

Any non-image field can be bound to a data source instead of a fixed value. The spot names the source and a dot path into it (`current.temperature_2m`, `daily.temperature_2m_max.0`, `events`). The static value is the fallback: it shows until the first data arrives, and whenever the live value does not fit the field. Before a bound value replaces it, the player checks it against the field's definition (type, `maxLength`, `min`/`max`/`step`, `options`, a list's `maxItems` and row fields); a value that is missing at its path or fails is ignored for that spot and counted against its source. So a template can trust its data to have the shape its fields declare, live or not. The check is `boundValue` in `packages/contract` (`validateBoundValue` on the value read), which the server also runs before it stores or sends a snapshot. Data the server has not confirmed for a day is stale, and the static value shows again (`SNAPSHOT_STALE_MS`). A news feed's `language` is always present (`''` when the feed declares none), so the news template binds it to write headline ages in the feed's language.

**Declaring live fields.** A template whose fields come from a feed says so in `live`, so the CMS shows a Source section for them instead of inputs: people choose where the data comes from (a place, a news feed, a calendar), never the values. Each field keeps its definition and default, which are the fallback.

```json
"live": {
  "source": "open-meteo",
  "fields": { "temp": "current.temperature_2m", "high": "daily.temperature_2m_max.0", "code": "current.weather_code" },
  "place": "city",
  "units": { "temperature": "unit", "wind": "windUnit" }
}
```

- `source`: the kind of feed. `open-meteo` is an Open-Meteo forecast (a JSON source; the CMS asks for the `current=` and `daily=` variables every base template reads, and any other the paths read — omitting `time`, which Open-Meteo always includes and rejects in the variable list — in the place's time zone, with `timeformat=unixtime`; so every spot for one place and units shares one source, #345). `rss` is a news feed and `ical` a calendar, which the server converts to `NewsFeed` and `CalendarFeed`, so their paths are those shapes' (`items`, `language`, `events`). A calendar event names its organiser by display name (`organizer`, the ORGANIZER's CN, or `''`), never by address: a name holding an `@` is `''` too. The feed holds only events that had not ended when the server read it, so room-status shows "Free all day" once a day's last meeting is over and polled away. A template cannot yet tell that its bound fields are playing their fallback: until `init` says so, a room-status spot whose calendar is missing or stale (no data, or none confirmed for a day) shows its fallback, no bookings, and so reads "Free all day". `table` is a CSV file or a JSON list at a link (below): its fields must be lists, at `rows`, and they stay typed until a spot binds them.
- `fields`: each live field's path in the snapshot, as a binding names it (`BINDING_PATH`). Not an image field.
- `place` (Open-Meteo only): a text field that starts as the name of the place picked. People may still change it.
- `units` (Open-Meteo only): the select fields that choose the units the forecast is fetched in, `temperature` with options from `°F`, `°C` and `wind` from `mph`, `km/h` (`WEATHER_UNITS`). The CMS sets them with the place, so the numbers and the unit shown always agree. A template that names no `wind` field gets wind speeds in the unit that goes with its temperature, km/h with `°C` and mph with `°F`, and reads a source the org has for the place and temperature in either wind unit (#541): one that shows a wind speed names its `wind` field, rather than printing a unit itself.

**Several sources.** A template whose fields come from more than one feed, such as the weather from Open-Meteo and the headlines from a news feed in one frame, names each source under `sources` (#193). Each named source takes the keys above, and a `label`, which the CMS shows over that source's picker; the Source section has one picker for each.

```json
"live": {
  "sources": {
    "weather": { "label": "Weather", "source": "open-meteo", "fields": { "temp": "current.temperature_2m" }, "place": "city", "units": { "temperature": "unit" } },
    "headlines": { "label": "Headlines", "source": "rss", "fields": { "items": "items" } }
  }
}
```

- A name is an id (`ID_PATTERN`). A field is fed by one source at most, and a field a source names as its `place` or `units` is one no source fills and no other source names: picking a source sets those fields, so two sources sharing one would overwrite each other.
- A spot binds each field to a data source of its own, so each source goes stale, fails or falls back on its own: the weather can show its fallback while the headlines stay live.
- `liveSources` in `packages/contract` reads either form by name; the one source of a template that declares one is named `source`.
- A template that declares `sources` needs manifest schema 7 (`MANIFEST_SCHEMA`). A player before #193 refuses it in any manifest, so the server tells it to reload (`canPlay`), as for schema 4. Templates that declare one source are unchanged.

`validateTemplateManifest` checks all of it. A template with no `live` is typed by people. The base templates: weather (`open-meteo`), news (`rss`: `items`, `language`), agenda and room-status (`ical`: `events`), menu-board (`table`: `items`), and info-frame (two sources: `open-meteo` as `weather`, with `timezone` and the next three days from `daily.<variable>.1` to `.3` including `daily.time.1` to `.3`, and `rss` as `headlines`: `items`).

**Table bindings.** A `csv` or `json-table` source's snapshot is a `TableFeed`: `columns` and `rows` of text and numbers (`@signforge/feeds`, Tables). A binding with a `table` mapping (`TableMapping`), at path `rows`, fills a list field from its rows:

```json
"items": {
  "source": "lunch-menu",
  "path": "rows",
  "table": {
    "columns": { "name": "Item", "price": "Price", "description": "Notes" },
    "filter": { "column": "Section", "equals": "Mains" },
    "sort": { "column": "Price", "descending": true }
  }
}
```

- Each row becomes an item: the column named for each item property fills it, converted to the property's type. A number written into a text property takes the screen's locale, as a price (4.5 is "4.50" in en-US, "4,50" in de-DE, 12 is "12"); text stays as the file has it ("$4.50"). A select takes its option in any case; a boolean `true`/`yes`/`1` or `false`/`no`/`0`. A date takes `YYYY-MM-DD` and a datetime `YYYY-MM-DDTHH:mm`, also written with a space for the `T` or with `:00` seconds, as spreadsheets export them; any other form (`27/11/2026`, an offset or `Z`) does not fit. An empty cell takes the property's default.
- Every property without a default needs a column. A row that leaves one empty, or does not fit the item (too long, not an option), is left out and named in the screen's rejected data; the rest still show. When every row the filter keeps is left out, the binding has no value: the poller fails the source as `unfit` and keeps the last good snapshot, and a screen keeps what it shows, rather than draw an empty list. A filter that keeps no rows is an empty list.
- `filter` keeps the rows whose cell equals the value, ignoring case and surrounding spaces; `sort` orders by a column (numbers, and text that is one number, by value; a date and time by time, whether written with a `T` or a space; other text in the screen's locale), else the file's order. Then the list is cut to the field's `maxItems`, so a template draws at most that many rows however long the file is. Measured on the Pi: menu-board fed by 24 rows plays as its 12 typed items do (`spike/pi-perf/RESULTS.md`, Table bindings).
- A table without a mapped column gives no items. The poller fails such a source as `missing-column` when a published spot maps the column, keeping the last good snapshot, and the sync and the screen refuse such a snapshot too, whatever else it fills: the last good rows stay on screen. A spot that plays one anyway (from a snapshot kept before the mapping changed) shows its fallback.
- A template that declares a `table` source, or a binding with `table`, needs manifest schema 4 (`MANIFEST_SCHEMA`). A player before #84 plays schemas 2 and 3 and refuses such a template in any manifest, typed items or not; it reports that in its sync, cannot play schema 4, and the server tells it to reload (`canPlay` in the contract's `playable.ts`, which sync calls), into a player that plays 3 and 4.
- A table with more cells than any snapshot can hold (columns × rows past half `MAX_SNAPSHOT_BYTES`) is refused as `too-large` before its rows are built.

A spot may still bind any field to any source with the tools (`bindings` on `save_spot`); `live` is what the editor offers.

The server fetches feeds, never the screen. JSON feeds pass through; calendar (iCal), news (RSS or Atom) and table (CSV, or a JSON list) feeds are converted to fixed shapes, `CalendarFeed`, `NewsFeed` and `TableFeed` in `packages/contract`, so a template binds to the same paths whichever service the data came from. A news story carries its photo (`image`, #196) and its description as plain text (`summary`, at most `NEWS_SUMMARY_MAX` characters, #202) when the feed has them. A spot reads the latest data when it starts; data does not change during a play.

## Rules

Each rule comes from a measurement on the baseline device, a Raspberry Pi 4 at 1080p 60 Hz. The numbers are in `spike/pi-perf/RESULTS.md`.

**Layout**
- Size everything relative to the viewport (`vmin`, `vw`, `vh`, `%`). No fixed pixel sizes.
- Handle every orientation you list.
- Read sizes from `ctx.viewport`, not `innerWidth` or `innerHeight`. While a template prepares, its frame may not be laid out yet and the window reports 0.

**Animation**
- Animate `transform` and `opacity` only. Do not animate layout properties such as `width`, `top` or `font-size`.
- No `backdrop-filter`. The build rejects it. A translucent gradient panel gives a similar look for free.
- Prefer effects the browser draws once over CSS `filter`. `box-shadow`, `text-shadow`, gradients and gradient text are rasterized once and cost nothing afterwards. `filter: blur()` and `filter: drop-shadow()` are reapplied on the GPU every frame. One template can afford a few, but a transition puts two templates on screen and doubles the cost. A soft glow is a radial gradient; a product shadow is a blurred-looking radial gradient underneath it.
- At most about 50 elements animating at once.
- For particles (rain, snow, confetti), draw a small seamless tile once, use it as a repeating background, and slide the element by one tile with a CSS animation. Measured on the Pi: under 0.4% dropped. Redrawing a full-screen canvas every frame, or sliding one giant canvas, stalled for up to half a second.
- Do not run a `requestAnimationFrame` loop. Anything that must update over time (a clock) should change text at most once a second.
- Give each element an intro and an outro. The player may crossfade or cut between spots; it does not animate your content.
- Spots can be any length in your range. Do not assume the default duration: derive end-of-spot timing from `--sf-duration`.

**Text**
- Fit the space you have. Clamp long text with `-webkit-line-clamp` or `text-overflow: ellipsis` (or `fitWords` to end on a word), and show as many list rows as fit rather than a fixed count, dropping those that do not fit rather than letting them run off screen (see `templates/agenda/main.ts`).
- Give grid and flex tracks a zero minimum (`minmax(0, 1fr)`, `min-width: 0`). A track's default minimum is its content's width, so one unwrapped line (`nowrap`, a long headline) widens the whole column past the screen and every clamp or ellipsis in it stops working. Found on live news feeds.
- A crawl or ticker is one strip of text holding its content twice, sliding left by exactly one copy. It loops seamlessly and costs nothing measurable.

**Isolation**
- No network. The template runs in a sandboxed frame under a policy that blocks every request, including navigating its own frame: a template that tries is stopped and its spot is skipped. There is no WebRTC either: `RTCPeerConnection` is undefined in the template's frame and in any frame it adds, on screens and in the runtime check. Scripts and styles must be inline after the build, and images arrive from the player.
- Only the bundle's own inline classic scripts run (no `type`, or `text/javascript`), and each must start with exactly `"use strict";` (`sf build` makes one such script: esbuild emits it for a strict TypeScript build). Scripts are read with an HTML parser: a script example shown in a textarea or kept in a comment is text, and is left as written. A template may not hold a `<select>`: a screen takes no input, so use text or an image. Browsers also parse what is inside one differently, so nothing in it runs. Inline modules, external scripts (none is ever requested), inline event handlers (`onclick="…"`, `setAttribute('onload', …)`) and `javascript:` URLs do not: use `addEventListener` or a property (`img.onload = …`). Nor do `eval` and `new Function`.
- No storage, cookies or access to anything outside its own frame.
- Fonts ship inside the bundle. Reference a font file from `style.css` and the build inlines it. Use a font you are licensed to redistribute, and carry the notice its licence asks for: every font the shipped templates inline is under the OFL 1.1, which asks that each copy carry the font's copyright notice and the licence, so their `style.css` (or the look kit's `looks.css`) opens with a `/*! … */` comment holding both, which the build keeps in the bundle (about 4.8 kB for Inter alone). `packages/cli/test/templates.test.ts` fails for a shipped template whose bundle inlines a font without the OFL, or a font without the copyright line from its package's `LICENSE`. Brand fonts are the exception: they come with the theme (see Brand), from the curated catalogue in `fonts/`.
- Data is fixed for one play. New values arrive with the next `init`, from a clean document (see Lifecycle).
- Decoration must not fail the spot. If an optional effect cannot be drawn, catch the error and show the content without it; a template that rejects in `prepare` is skipped.

**Budgets**

| Limit | Value |
| --- | --- |
| Built bundle size | 600 kB |
| `init` to `ready` | 500 ms, brand fonts included |
| The first prepare after a page load | about 600 ms, typical (pending the owner's confirmation, #232) |
| Brand font family (all weights, WOFF2) | 150 kB |
| Dropped frames over a play | 1% |
| Longest single frame | 50 ms |

The 500 ms budget protects the spot on screen while the next one loads. The page's first prepare has none: nothing is drawn yet, so it drops no frames, and it pays once for what every later prepare finds ready (the player reads the bundles still to come while a spot plays). A look-kit template's first prepare took 455 to 558 ms on the Pi (one of 948 ms), against 220 to 330 ms for a later one (`spike/pi-perf/RESULTS.md`, A template's first prepare), so it is held to about 600 ms, as typical rather than a ceiling.

`sf build` and `sf template push` enforce manifest validity, the forbidden-CSS list (on the bundle: `backdrop-filter`, and an `@import` the build did not inline), bundle size, the no-network rule and the forbidden-code list (`checkTemplateBundle` in `packages/contract`; it refuses network calls, navigation, inline event handlers and `javascript:` URLs) and the script rule (read with an HTML parser: each classic script in HTML or SVG starts with exactly `"use strict";`; no external script, module or other script type, and no `<select>`), and warn on colour literals (see Brand). In the bundle's styles the no-network rule looks for quoted strings and `url()` addresses that start with `//`, `http://` or `https://`, since `image-set("//…")` fetches one with no `url()` around it: decorative text such as `content: "// live"` is refused too, so put it in the markup. A backslash counts as a slash, since the URL parser reads one as `/` in an `http(s)` address (`"\\\\host"` is `//host`); a string that starts with two backslashes is refused even where it is a path. Each `<style>` element and `style` attribute is taken from the bundle's HTML parse (parse5, the parser the script rule uses), so its text is what the browser's is: an HTML `<style>` is raw text to its end tag, an SVG one has its character references read, its CDATA unwrapped and its comments left out, an attribute's value has its references read, and a `<style>` inside a comment or a script string is none. What a `<select>` holds is not read: the bundle is refused for the `<select>`. The styles are then read twice: as written, where a comment that quotes such an address stays in sight and a quote followed by `//*` or `https:/*` is refused wherever it is; and as CSS reads them, with comments, line continuations and escapes (`\2f`, `u\72l(`, `@\69mport`) undone, an escaped quote starting and ending no string, an unquoted `url()` read as one token (a name of exactly `url`, then `(` and CSS whitespace only, as CSS Syntax 3 reads it), and the control characters the URL parser drops left out of strings and `url()`s. The forbidden-CSS list is checked on both readings. The server repeats the same checks when a version is registered and stores the report on it: the first four on the uploaded bundle, the code list on the author's own `index.html`, `style.css` and `main.ts`, which are uploaded alongside it (the bundle holds the SDK, which itself calls `parent.postMessage`).

These checks are a lint, not a security boundary: they match text, and an address written another way gets past them. Known ways: a scheme with no slashes (`"https:host"`), `srcset` and `poster`, a `src` or `href` unquoted or with a space before the address, and any place where the lint's reading of the HTML or CSS still parts from the browser's. What keeps a screen safe is the sandbox the template runs in, with its policy that blocks every request, and the runtime check (below), which refuses a version that makes one.

**The runtime check.** The server then renders an org's new version before registering it (`apps/template-check`; docs/architecture.md, Runtime check): headless Chromium in a container with no network, in the player's own frame and policy, with each field's default (a small image for each image field), at 1920x1080 in each orientation you list. It plays for a second after `ready`. The version is refused with each of these it sees, one sentence each:

- a request of any kind (`requested https://example.com/x (blocked)`), including images, fonts, media, workers and beacons, and anything else the policy blocks (`eval`);
- navigating its own frame, the page around it, a new window or a form;
- an uncaught error, or a `prepare` that rejects. Its frames have no `RTCPeerConnection`, as on a screen, so a template whose use of it throws is refused this way; one that catches the error, or only tests for the constructor, passes (and has no WebRTC on screens either);
- no `ready` within 2 seconds, the player's limit;
- `ready`, then no second of frames within 3 seconds of `play` (`froze after play`): a template wedged in `play`, as a busy loop is, would freeze the screen. Blocking work in `play` is refused once it runs for about 2 seconds, since the second of frames must still fit in the 3.

It runs in your org's own container, which no other org's template shares. A check that could not run (the container busy or not started) refuses the push as `unavailable`: try again. An org may run about 10 checks a minute (the count is kept per Cloudflare location). A pass is stored on the version with its timings (ms from `init` to `ready`, and the first second's frames, per orientation); they are information, not a gate, since the budgets are measured on the Pi. Base templates in `templates/` go through the same runner in CI (`apps/template-check/test/check.test.ts`). Test yours with `sf template push` to an org.

A registered version is immutable: pushing the same version with different bytes is refused, and pushing identical bytes changes nothing. A version is a draft, approved or retired; only approved versions are offered for new spots. The time and frame budgets are measured on the device with `scripts/pi-measure.sh`; automated checks for them are part of Milestone 4. Of the timings, the runtime check refuses only a template that is not ready within 2 seconds or that draws no second of frames within 3 seconds of `play`. It watches only the first second after `play`: a template that stops drawing later is not seen.

So a shipped template's bundle must not change under its version, or `sf template seed` refuses it on the next deploy. A bundle holds the template's own files, the SDK, the look kit in a template that imports it (see Looks), and from the contract only `@signforge/contract/frame` (the protocol version and the brand variables) and, in a template that reads an image's sample, `@signforge/contract/sample`, so a change to the rest of the contract (the API's, the sync's or the screen's checks) leaves every bundle byte for byte. `packages/cli/test/templates.test.ts` builds every template in `templates/` and compares each bundle's sha256 with `packages/cli/test/golden/template-bundles.json`, by template key: it fails when a bundle changed, whatever changed it. Then bump the version in the template's `template.json` and `package.json`, put the new key and hash in that file (the failure shows both), regenerate the goldens, and draw the New spot dialog's thumbnails again (`pnpm build:player && tsx scripts/template-thumbnails.ts --chrome <Chromium>`; `apps/cms/test/template-thumbnails.test.ts` fails until you do). A change to the SDK's index can change every bundle, even of templates that do not use the new code (an unused export changed six of seven, and two added to `@signforge/contract/frame` changed all seven; a comment-only edit changed none), because the minifier renames symbols across the whole bundle: SDK code only some templates use goes in its own entry point, as `readableOn` does. An esbuild or bundled-font upgrade turns the test red for every template the same way.

## Review checklist

For a human approving an agent-built template:

1. `sf build` passes with no problems reported, and the version registered, so the runtime check passed (its report is on the version).
2. It looks right in both orientations it lists, at the shortest and longest duration in its range.
3. Long field values do not overflow or overlap (try each text field at its `maxLength`).
4. On the Pi, `device/pi/isolate.py 30 cut <spot>` reports under 1% dropped frames while playing, and no frame over 50 ms.
5. Fonts and any artwork baked into the bundle are ones we may redistribute.
