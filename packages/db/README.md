# @signforge/db

The D1 schema, its migrations, and the only code allowed to query tenant tables.

## Using it

```ts
import { scoped } from '@signforge/db';

const org = scoped(env.DB, orgId);
await org.screens.get(screenId);        // undefined if the screen is another org's
await org.playlists.setItems(id, spotIds); // throws NotInOrgError if any id is not this org's
```

Every repository query is filtered by the scope's org, and every row it writes is stamped with that org whatever the caller passes. A call made for org B with org A's ids reads nothing and changes nothing. Templates and template versions with a null org are base templates: every org can read them, none can change them.

The table objects (`src/schema.ts`) are not exported. `test/node/boundary.test.ts` fails if anything outside this package imports them; code elsewhere imports `@signforge/db`. Only tests, their harnesses and e2e specs (in a package's own top-level `test` or `e2e` directory, not such a folder under `src`) and `apps/api/scripts/dev-screen.ts` may also import `@signforge/db/testing`: the same test fails if production code does.

`@signforge/db/testing` has `seedTwoOrgs(db)`: two orgs, `org-a` and `org-b`, each with one of everything, for isolation tests. `seedOrganization(db, orgId)` writes just the `organization` row, which every tenant row needs. `testScope(db, orgId)` is `scoped(db, orgId)` with `insert(values)`, `update(id, patch)` and `delete(id)` on each repository, so a test (or `apps/api/scripts/dev-screen.ts`) can set up a row in one line. Each is the repository's `stage` write committed at once, so it checks and stamps rows as a tool's write does, and each reports what D1 did: `update` of a versioned row is guarded by the version it read, so the version it returns is the one stored and a change that landed in between refuses it (`StaleVersionError`); `update` returns undefined and `delete` false when D1 changed no row of the org's (another org's, a base template, one already gone). `connections.authorizations` has only `insert`: production never changes an authorization, so a test expires one with the clock. Production code never writes that way: it stages, below.

Code that has to find a row before it knows the org (device auth by screen id, pairing, the data-source poller) gets a narrow function here, added by the ticket that needs it. It does not get the tables. So far:

- `findMembership(db, orgId, userId)`: re-checks the active org on every `/api` request.
- `startingOrg(db, userId)`: the org a new session starts in (the user's only org, or the one they last made active while still its member; else none), for Better Auth's session create hook in `apps/api` (#182). Triggers on `session` remember each switch of a session's org on the user (`session_org_remembered`, 0029, replaced in 0030) and clear a new session's org whose membership ended after this read (`session_org_is_a_membership`, 0029). drizzle-kit does not model triggers, so a migration that rebuilds `session` or `user` must create both again, and renumbering 0029 or 0030 must keep them.
- `findDeviceScreen(db, screenId)` (`src/device.ts`): a screen's org, desired and previous manifest ids, and the hashes of its unrevoked credentials (each with whether it was used yet) (none if the screen is revoked). The device API checks the secret against them, then uses `scoped(db, orgId)`.
  The temporary `/admin` upload routes (M3-04) also use it to find a screen's org, behind the deploy secret. The publish they end with goes through the tool registry with `scoped(db, orgId)`.

- `claimDueDataSources(db, now, { limit, leaseMs })` (`src/poller.ts`): the poller's (`apps/api/src/data`). It claims the sources whose `next_poll_at` has come, in every org, by moving it on by the lease in one statement, so overlapping runs never fetch a source twice, and returns only each one's org and id. The poll then reads and saves through `scoped(db, orgId)`.
- `organizationExists(db, orgId)`: the `/admin` template routes check the org they are told to write to.
- `findAlertWork(db, now, defaultUnreachableMs)` (`src/alerts.ts`) and `orgMembers(db, orgId)`: the API's offline alert check (M3-42). The first lists, across orgs, screens with a live credential silent past their org's threshold and no open incident, and open incidents whose screen has been heard from since; the second, an org's members with their user id, address and role. The check then writes through `scoped(db, orgId).incidents`: `open(screenId, lastSeenAt, now, alert?)` returns the new incident's id and `clear(incidentId, now, alert?)` whether it cleared it, each only for the call that made the change, so of two overlapping checks only one alerts. `alert` is the Slack and webhook deliveries to queue (#88), written in the same batch as the incident: both or neither, and an offline alert only by the call that opened the incident. `screen_incidents` allows one open incident per screen (a partial unique index).
- `claimDueAlertDeliveries(db, now, { limit, leaseMs })`, `alertChannelsOf(db, deliveries)` and `settleAlertDeliveries(db, now, settled)` (`src/deliveries.ts`): the API's alert delivery run (#88), one D1 query each however many deliveries it takes. The claim takes the pending deliveries whose next attempt has come, in every org, counting the attempt and holding it for the lease (`leased_until`) in one statement through `alert_deliveries_due_idx`, which holds only pending rows, and returns the rows. The settle records each attempt's result only if it is still the latest attempt, and ends the claim. `org.alertDeliveries.claim(id, now, leaseMs)` and `settle` do the same for one delivery in an org (a test send or a retry), and `stage.retry` changes nothing while a claim holds the delivery.
- `expireIdempotencyKeys(db, now)`, `expireAuditRows(db, now)` and `expireAlertDeliveries(db, now)` (`src/retention.ts`): the API's daily retention job (F13, #41; #88). They delete, in every org, idempotency keys and alert deliveries older than 7 days and audit rows older than the org's `org_settings.audit_retention_days` (null: `DEFAULT_AUDIT_RETENTION_DAYS`, 365), and read nothing. Audit rows and alert deliveries go in batches of 1,000, at most 10 a run (`AUDIT_ROWS_PER_RUN`), org by org through `audit_log_org_at_idx` and `alert_deliveries_org_created_idx`; a larger backlog goes over the next runs, and one org's backlog delays the orgs after it in id order until it is cleared (the API logs a run that hit the cap). Each deleted row counts towards D1's rows-written allowance, with its indexes; check `rows_written` from a production run before raising the cap. `expiredFeedImages(db, now, limit)` and `pendingFeedImageDeletes(db, now, limit)` are also in `src/retention.ts` as named cross-org exceptions for the 01:00 UTC feed-photos sweep, sharing the rules and constants of `src/feed-photos.ts`.
- `startPairing(db, { code, pollTokenHash, now })` and `collectPairing(db, pollTokenHash, now, mint)` (`src/pairing.ts`): the screen's half of pairing. `startPairing` stores a code for 15 minutes (`PAIRING_TTL_MS`), sweeping codes past their time in the same batch, and returns false if the code is in use. `collectPairing` answers `waiting` or `expired` until the code is claimed; then it mints the credential and stores it with `scoped(db, claimedOrg).pairing.collect(...)`, the org being the one the claim stored on the code, never one the screen names. A repeat poll (a lost reply) replaces that credential with a fresh one while it is unused and the first collect was under `PAIRING_TTL_MS` ago; each step of the batch is guarded on the code still naming the credential it replaces, so of two racing polls one writes. `org.screens.credentials.markUsed(id, now)` records a credential's first use (device auth, once per credential): a used credential is never replaced.

`org.pairing.open(code, now)` says whether a code can be claimed now (unknown, expired and claimed are all false), and `org.pairing.stage.claim(code, screenId, now)` binds it to a screen staged before it in the same batch. Its second statement makes the whole batch fail, writing nothing, if the code was not open when it ran.

Base templates are written by `platform(db)` (`src/platform.ts`), the one scope that is not an org's. It reads and writes only rows with a null org: `templates`, `template_versions`, and the `platform_audit_log` that records each change. Its `templates` has the same shape as an org scope's, so one tool serves both. Only `/admin` uses it, through the tool dispatcher's platform registry. `org.templates.ownByKey(key)` and `org.templates.versions.ownVersion(templateId, version)` return the scope's own rows only, never base ones.

`org.screens.setDesiredManifest(screenId, manifestId)` keeps the manifest it replaces as `previous_manifest_id`, whose files a screen mid-switch may still fetch.

`org.screens.sync(screenId, write)` is a screen's sync in one atomic batch: its heartbeat, last-seen time and active manifest, and its hourly play counts added if the batch's `seq` is above the highest stored in its `epoch`. Each epoch keeps its own mark (`sync_epochs`), so after a re-image retries from the old and new epochs count once in any order. The repeat check is inside the SQL, so a retried or doubled request counts once. It returns the highest stored `seq` and the rows D1 wrote. `org.screens.reportManifest(screenId, id, { observedAt, arrivedAt })` is the socket's report of the active manifest. Both replace the reported manifest only with one the screen observed later (`reported_manifest_at`); a report without a trusted time is ordered by arrival. Neither moves the screen's version.

`org.dataSources.savePoll(id, { source, snapshot?, checkedAt?, photos? })` saves what one poll found in one batch: the source's patch (next poll, failures, error category, ETag), and either a changed snapshot or, for a feed that still says the same, only the snapshot's new `checked_at`. For a news source, `photos` (`src/feed-photos.ts`: `photoRead`, `pollSave`) guards the save on the source's version, holds due and budgeted photo URLs in the same batch when the save stands, and leaves an unconditional reread due when the save is stale or a copy changed in flight; it returns `{ stood, held }`. `org.dataSources.snapshots(ids)` returns each snapshot with its `checkedAt`, which sync sends a screen.

Feed photos (#195, #329; `src/feed-photos.ts`): `org.feedPhotos` is composed into `OrgScope` and owns the D1 half of a news story's photo behind six methods (`get`, `plan`, `copyOf`, `delivered`, `expire`, `deleteBlobs`), along with the `sourceEdited` and `pollSave` rules applied inside `dataSources.stage.update` and `dataSources.savePoll`, `photoRead`, the snapshot-reference rule (`namedBySnapshot`), and every feed-photo timing and budget constant. No caller has to call two methods in a set order: `savePoll` holds photo URLs in the same batch as the snapshot save, `delivered` claims hashes before calling `write` and saving the row, and `deleteBlobs` leases due hashes, calls `remove`, and clears them.

Connections (#83): `org.connections` holds the org's connected provider accounts, with their credentials sealed (`credentials_sealed`, opened only by the API's connector code). The poller changes a connection only while it still holds the grant the poll read: `saveGrant(id, from, { credentialsSealed, expiresAt })` after a refresh, which also makes it active again (a racing run may have marked it refused first), and `markNeedsReconnect(id, from, lastError)` when the provider refused it; both return whether they wrote, so a refresh that finishes after another run's, or after a person reconnected, changes nothing. `org.connections.authorizations` holds the OAuth authorizations members started: `byState(stateHash, now)` finds a live one in this org only, `stage.consume(id)` deletes it in the batch that finishes it and fails the batch unless that delete removed it, so a state works once, and `stage.deleteExpired(now)` drops the ones that ran out. `org.dataSources.usingConnection(id)` lists the provider sources that read through a connection, and `org.dataSources.stage.pollAgain(id)` makes them due at once with their failures cleared (a reconnect), leaving their versions alone.

`org.screenGroups.setMembers(groupId, screenIds)` replaces a group's members in one batch, after checking the group and every screen are the org's (`NotInOrgError` otherwise, changing nothing). Staged, `stage.setMembers(group, screenIds, { newGroup?, ifVersion? })`, `stage.addMembers(group, screenIds, ifVersion?)` and `stage.removeMembers(group, screenIds, ifVersion?)` take the group as read and move its version on.

`org.assets.usage(assetIds?)` maps each asset to the ids of the spots that use it, through an image or video spot's `asset_id` or a template spot's asset map. Unused assets are absent. The asset tools use it for usage counts and to refuse deleting an asset in use.

### Staged writes

D1 has no interactive transactions, but a `batch()` is atomic. So each repository also has a `stage` (`src/writes.ts`): `org.screens.stage.update(row, patch)`, `org.assets.stage.insert(values)`, `org.screenGroups.stage.setMembers(group, screenIds)` and so on build the statements of a change without running them. They return `{ row, writes }`: the row as it will be once written (ids, timestamps and column defaults are fixed when staged, so it is exact), and opaque `Write`s, stamped with the scope's org like every other write. `org.commit(writes)` runs them in one batch: all take effect, or none. A row's own insert, update and delete exist only staged (`testScope` commits them for tests). `platform(db)` has the same `stage` on `templates` and `templates.versions`, and its own `commit`.

The tool dispatcher (`packages/tools`) is what commits: a tool stages its change, and the dispatcher commits it with its audit row (`org.auditLog.stage(...)`) and, for a keyed creation, its idempotency record. `org.auditLog.append(...)` writes a row on its own, with no change to commit it with: the API's membership hook (`membershipAudit` in `apps/api/src/auth/options.ts`) uses it for the changes Better Auth makes, which run outside our batches, and tests use it to seed. `org.auditLog.appendOnce(key, ...)` writes a row at most once per key in the org, however many calls race to write it: the dispatcher's one row per agent grant and limit window (`packages/tools`, Agent limits). Its id is `aud_once_` and 40 hex digits of a SHA-256 of the org and the key, so it fits the contract's `ID_PATTERN` and no org's row stands in for another's (`test/audit-once.test.ts`). Each audit row records the actor kind and id, the client id (`client_id`: `cms`, `sf-push`, an agent's OAuth client), the action, the target and a redacted detail. `org.auditLog.list(...)` reads a screen's recent events; `org.auditLog.page(...)` reads one page of the whole log in SQL, newest first, keyed by `at` and `rowid` and filtered by actor, action, target, time and text, for `list_audit_log`.

### Row versions

Screens, screen groups, brand kits, data sources, spots, playlists and schedule entries have a `row_version` (`rowVersion`): 1 when inserted (a draft made again with a deleted one's id continues from its last, below), and one more with every `stage.update` and `stage.touch`, and for a playlist with `setItems` or a `stage.update` that replaces its items (no caller sets it; heartbeats, `setDesiredManifest`, `dataSources.savePoll` and a draft's `stage.publish` leave it alone). `stage.update(row, patch, ifVersion)` and `stage.touch(row, ifVersion)` refuse a change made from an old read: they throw `StaleVersionError` (`{ id, version }`, the version now) at once if `row` is already another version, and otherwise stage a first statement that fails the batch if the row is no longer `ifVersion` when it runs. `commit` then throws `StaleVersionError` too (`NotInOrgError` if the row is gone), and nothing in the batch is written. A guard aborts its batch with an error naming `GUARD_ABORT`; if one failed it but every guard holds again by the time the failure is diagnosed (a change made and taken back since), it is still a `StaleVersionError`, with id `batch` and version 0: a conflict, never the database's raw error. Any other failure of the batch is the database's error, as it is. `stage.touch` moves a row's version and `updatedAt` on without changing its fields, for a change to what belongs to it (a group's members). The column is not `version` because a template version already has one, its semver.

### Drafts and published versions

Spots, playlists and schedule entries have a draft and a published version (`src/drafts.ts`, docs/backend-plan.md#publishing). The row's columns are the draft: `stage.insert` and `stage.update` change only them, and drop `publishedJson` and `publishedAt` if a caller passes them. `org.spots.stage.publish(row)`, `org.playlists.stage.publish(row, items)` and `org.scheduleEntries.stage.publish(row)` stage copying the row's content as read (a playlist's with its items) into `published_json`. Each is guarded by the row's version as read, as `stage.update` is, and by its `incarnation`, a random id fixed at insert (null on rows made before migration 0019), a second check now that versions never repeat (below). A draft edited since (a playlist's items too), deleted, or deleted and made again, fails the batch with `StaleVersionError` (version 0 for one that is gone, so a publish gets `conflict` and can load again, not `not_found`) and nothing is written. Publishing is not an edit: the version stays, and `updated_at` is left as stored. `published(row)` returns the published version shaped as the row (a playlist's with `items`), or undefined if it was never published; `draftChanged(row, items?)` says whether the draft differs from it.

Versions of a draft's id never repeat within an org (#64). Deleting a spot, playlist or schedule entry, by any path (`stage.delete`, `stage.remove`, or a schedule entry's cascade when its screen or group goes), leaves a tombstone, its id and last version (`draft_tombstones`, written by `AFTER DELETE` triggers from migration 0020); `stage.insert` of that id starts one above it, so an edit or publish guarded by a version read before the delete is refused. Another org's same id starts at 1. `stage.insert` on these three is async: it reads the tombstone to return the row's version, exact unless a delete of the same id commits in between or is staged earlier in the same batch, when the stored version is higher (an edit from the returned row is then refused, never let through). Tombstones are never pruned: one small row per deleted id per org, about 200 MB per million deletes against D1's 10 GB. drizzle-kit does not model triggers, so a migration that rebuilds one of these tables (as 0010 did) must create its trigger again, and renumbering 0020 must keep the hand-written triggers. The same holds for `session` and `user`, whose triggers come from 0029 and 0030 (`startingOrg` above). And for `member`: `member_keeps_an_owner_on_role` and `member_keeps_an_owner_on_delete` (0036, #292) refuse a role change or delete that would leave an org with no owner, so a migration that rebuilds `member`, or renumbers 0036, must keep them. They watch `role` and deletes only: a write that moves an owner's row to another org, or an `INSERT OR REPLACE` over it, gets past them, and no code does either.

`org.playlists.stage.insert(values, items?)` stages a playlist with its spots in play order. `org.playlists.stage.update(row, patch, ifVersion?, items?)` stages a change to the draft's fields and, with `items`, its order replaced whole: the version moves on once, guarded by `ifVersion` as every `stage.update` is. Both throw `NotInOrgError` for a spot the org does not have. `org.playlists.allItems()` and `org.screenGroups.allMembers()` read every playlist's items and every group membership in one query each, for a publish. `org.settings.get()` and `org.settings.stage.set(patch)` hold the org's settings: the default playlist, refused (`NotInOrgError`) for a playlist the org does not have, and since M3-42 the defaults for new screens, the update window, the alert threshold and the alert rules (`packages/tools` `src/settings.ts` reads them with their defaults). `stage.set` changes only the fields given and moves the settings' `row_version` on; `stage.set(patch, ifVersion)` is guarded as `stage.update` is, counting an org with no row as version 1. `org.alertChannels.stage.put(kind, values, ifVersion?)` is the same for an alert channel (an absent one is at version 0): both are one upsert in `scoped` for a single-row versioned record, and every version check inside a batch, theirs, a row's and a publish's, is one guard statement (`staleGuard`). The row also holds the org's publish revision (`publish_revision`, 0 with no row), which only `org.publishes.stage.advance(revision)` moves: it stages a guard that fails the batch (`StaleVersionError`, id `publish revision`) unless the revision is still the one the publish read, and moves it on without touching the settings' version or `updatedAt`. An org with no row gets one, at revision 1, every setting at its default and the version at 1, so the first publishes are ordered too; its `updatedAt` is that publish's time. Committed in one batch with a publish's screen switches, it puts publishes in order: one that read before another committed writes nothing. `org.publishes.stage.addScreens(publishId, rows)` stages a publish's rollout rows (`publish_screens`) for that batch, after the publish's own `stage.insert`, so a refused publish leaves no row, no rollout and no switch behind. `org.assets.usage` counts a spot's draft and its published version, so an asset a screen still plays counts as used.

`org.idempotency.get(key)` and `org.idempotency.stage({ key, action, inputSha256, outputJson })` read and stage the `idempotency_keys` record of a creating tool call, keyed `(org_id, key)`: a second record of the same key fails its whole batch.

## Better Auth's tables

`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`, `rateLimit` and the OAuth provider's `oauthClient`, `oauthResource`, `oauthClientResource`, `oauthConsent`, `oauthAccessToken`, `oauthRefreshToken` and `oauthClientAssertion` (M4-04) are defined in `src/schema.ts` as Better Auth's CLI generates them for `apps/api`'s options (camelCase columns, `date` columns holding ISO strings), and migrated like any other table. Better Auth reads and writes them itself through the D1 binding. The provider's consents and tokens carry an agent grant's id as `referenceId` (indexed, our addition). Agent grants (`agent_grants`, M4-04) are a tenant table: `org.agentGrants` (`get`, `list`, `unrevokedFor(userId)`, `touch(id, now)`, `stage.insert`, and `stage.revoke(grant, by, now)`, which in the same batch deletes the provider's access tokens, refresh tokens, consents and unexchanged authorization codes (`verification` rows whose JSON names it) for the grant, found in the scope's org first). `agentGrantForToken(db, tokenHash, resource, now)` (`src/agent-grants.ts`) is the per-call check across orgs: one statement joining the token, its grant and the grant's user's membership, all live, so the org comes from the grant and a token without a grant row is not live. `pruneUnconsentedClients(db, now)` deletes clients registered over a day ago that nobody consented to, except the first-party `sf-cli`, which migration 0034 registers. `test/agent-grants.test.ts`. Our code only reads them: an org's `member` and `invitation` rows through its scope (`org.members.list()`/`get(id)` with each member's name and address, `org.invitations.pending()`/`get(id)`, `test/members.test.ts`), for the member tools (#108), which change them through Better Auth's endpoints; `findMembership`, `memberOrgNames`, `orgMembers` and `startingOrg` read across orgs for the API's checks. `seedTeam(db, orgId)` (`src/testing.ts`) writes an owner and a pending invitation as Better Auth would. `apps/api/test/auth-platform.test.ts` asks Better Auth whether anything is missing, so a plugin or option change that needs a new column fails there. To see what Better Auth wants:

```sh
cd apps/api && pnpm exec auth generate --config auth.config.ts --output /tmp/better-auth.sql --yes
```

Then mirror the change in `src/schema.ts` and run `generate`.

## Schema rules

From `docs/backend-plan.md#data-model-d1`, checked against the migrated database by `test/schema.test.ts`:

- Text ids matching the contract's `ID_PATTERN`; `newId(prefix)` makes them. Integer millisecond timestamps.
- Content rows (`spots`, `playlists`, `schedule_entries`, `data_sources`, `brand_kits`) are keyed `(org_id, id)`. Content and manifests name spot, playlist, entry and data-source ids, so `stage.insert` takes a caller's id for them (any `ID_PATTERN` id; two orgs may use the same). Every other tenant table keeps a global `id` primary key, and `stage.insert` always makes the id itself, ignoring one the caller passes: a screen's id must be unique across orgs (its credential and its Durable Object name it alone), and nothing else needs a chosen id. `platform(db)` makes base template ids the same way. Tests that need a screen with a fixed id (a golden manifest's) use `seedScreen(db, orgId, screen)` from `@signforge/db/testing`.
- Every tenant table has `org_id NOT NULL`; its indexes lead with `org_id`; every row is unique on `(org_id, id)`.
- References between tenant rows are composite `(org_id, x_id)` foreign keys.

Deliberate exceptions: `pairing_codes` is not a tenant table (a code exists before an org claims it); nor is `platform_audit_log` (changes made outside any org); `templates` and `template_versions` allow a null org for base templates; `spots.template_version_id` references a version by id alone, because it may be a base one, and the repository checks it; it checks too that the assets a template spot's `asset_map_json` names are the org's. `data_sources.connection_id` has no foreign key (adding a composite one to an existing table means rebuilding it): the repository checks the connection is the org's, and a source whose connection is gone fails its polls as `disconnected`. Every tenant `org_id` references Better Auth's `organization(id)`, without cascade. `brand_kits` is keyed `(org_id, id)` and its ids are always the server's. `brand_assignments` has no id; it is unique per target (the org, a group, a screen) by partial indexes.

Local D1 enforces foreign keys (`PRAGMA foreign_keys` is 1, and a test shows a cross-org row is refused). Production is verified in M3-00. Isolation does not depend on it: the repositories filter every query.

## Migrations

After changing `src/schema.ts`:

```sh
pnpm --filter @signforge/db generate         # writes migrations/NNNN_*.sql
cd apps/api && pnpm exec wrangler d1 migrations apply DB --local
```

`apps/api/wrangler.jsonc` points `migrations_dir` here. `0002_better_auth` rebuilds every tenant table to add the `organization` foreign key; it is safe only on a database with no tenant rows, which held for every environment when it was written. `0010_content_ids` rebuilds the four content tables with their new keys and keeps every row: D1 cannot turn foreign keys off, and dropping a parent fires its `ON DELETE CASCADE`, so it copies `playlist_items` and `data_snapshots` aside and puts them back (checked on a local D1 seeded before it ran). A later rebuild of a table with cascading children must do the same. Tests in both packages apply the same migrations to their local D1 before running.
