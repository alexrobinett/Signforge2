# @signforge/tools

One registry of operations on an org's data. The CMS calls it over `/api/tools`, and agents over `/mcp` (M4-06); WebMCP will too. Each is a thin adapter. Nothing else on `/api` changes data, and `apps/api/test/routes.test.ts` fails if a route tries.

## For the CMS: the route

Both routes run behind `requireOrg`. They need a signed-in session with an active org, and refuse an `Authorization` header. The caller acts in the session's active org only. No field in the request can choose another org. A CMS tab names the org it shows in `x-signforge-org` (`TAB_ORG_HEADER` in apps/api), and a call from a tab whose org is no longer the session's is refused with 409 `org_changed` before any tool runs (#129); the header never picks the org. Agents, scripts and the CLI send none.

### `GET /api/tools`

Lists the tools the caller's role may use:

```json
{ "tools": [{ "name": "rename_screen", "description": "…", "scope": "screens:manage", "minRole": "editor",
              "mutates": true, "inputSchema": { "type": "object", … }, "outputSchema": { "type": "object", … },
              "example": { … } }] }
```

`inputSchema` and `outputSchema` are JSON Schema, generated from the tool's zod input and output. A viewer gets only the read tools. Use the list to hide the controls a user cannot use.

### `POST /api/tools/:name`

- **Request.** The body is the tool's input as JSON, sent with `content-type: application/json`. Any other content type gets 415. An empty body counts as `{}`.
- **Success.** 200, and the body is the tool's output as JSON.
- **Refusal.** The body is `{ "error": code, "message": text, "details"?: … }`:

| Status | `error` | When |
| --- | --- | --- |
| 400 | `invalid_input` | The input fails the schema. `details` is `[{ path, message }]`, one entry per field. |
| 403 | `forbidden` | The caller's role or scopes do not allow the tool, or the caller lacks a service the tool needs (see Tool services). |
| 404 | `unknown_tool` | No tool has that name. |
| 404 | `not_found` | An id names nothing in this org, including another org's ids. |
| 409 | `conflict` | The change would break something else, or (with `ifVersion`) the row changed since the caller read it. `details` says what. |
| 429 | `rate_limited` | Too many attempts (`claim_screen`); try again in a minute. For an agent, its grant is over a limit (see Agent limits): `details` is `{ limit, retryAfterSeconds }`. |
| 503 | `unavailable` | A service the tool needs could not answer (`register_template_version`'s runtime check: its container did not start, is over its limit or its queue is full). Nothing was written; `details` is `{ retryAfterSeconds }`. |
| 401, 403 | `unauthenticated`, `no_active_organization`, `not_a_member` | Returned by `requireOrg`, before any tool runs. |

The CMS should keep every cookie a response sets (see M3-09). Times in outputs are milliseconds since the epoch.

## For agents: `/mcp`

Agents call the same tools over MCP (Streamable HTTP, stateless, JSON only) at `<CMS host>/mcp`, with an OAuth access token from the agent grant a person consented to (`apps/api/src/mcp`, the backend plan's Agents section). The adapter:

- builds the `Caller` from the grant alone: `org: scoped(db, grant.orgId)`, the member's role now, the grant's scopes, `actor: { kind: 'agent', id: <grant id>, clientId: <its OAuth client> }`, `agentLimiter`, and the API's `toolServices` without `members` (an agent has no Better Auth session, so `invite_member` and `cancel_invitation` are not offered);
- answers `tools/list` with `describeTools` for the grant, less any tool needing a service it lacks, each tool's input schema and hints (`readOnlyHint` from `mutates`, `destructiveHint` for `delete_*` and `revoke_*`, `idempotentHint` for keyed creations). A `tools/list` counts as one call against the grant's limit (`overLimit`), and over it is a JSON-RPC error `-32000` with `rate_limited`, the limit and `retryAfterSeconds` in its data;
- answers `tools/call` with `dispatch`: the output as `structuredContent` and as JSON text, or a refusal as a result with `isError` and `{ error, message, details }`. JSON-RPC errors are only for faults in the protocol, and an unexpected failure is a bare `-32603 Internal error`, its details only in the log.

Details:

- **Idempotency keys.** The creating tools (`create_group`, `create_asset_upload`, `create_video_upload`, `create_brand_kit`, `create_data_source`, `create_spot`, `create_playlist`, `claim_screen`) take an optional `idempotencyKey`: 8 to 128 printable ASCII characters the caller picks for one creation, such as a UUID. The CMS should send one with every create. A retry with the same key and input returns the first call's output and writes nothing, even when two calls race. The same key with a different input is refused with `conflict`. Keys are per org and kept about 7 days: a daily job deletes older ones (`expireIdempotencyKeys` in `packages/db`, from the API's five-minute Cron Trigger), after which a retry with the key creates again. A retried `create_asset_upload` returns the first call's upload URLs, which expire at their `expiresAt`. `register_template_version` needs no key: a version is registered once, and registering it again returns `changed: false`.
- **Conditional updates (`ifVersion`).** Screens, groups, brand kits, data sources, spots, playlists and org settings carry a `version` in their view: 1 when made (org settings: 1 until first set), moving on with every change through a tool (a group's also when its screens change, a playlist's when its spots do; a screen's not with heartbeats or publishes, a data source's not with polls). Every update tool takes an optional `ifVersion`, the version the caller read. If the row has changed since, the call is refused with `conflict`, `details: { id, version }` (the version now), and nothing is written; read it again and redo the change. The check runs inside the batch that writes the change, so a change landing between the tool's read and its commit is caught too. Without `ifVersion` a change is made whatever the version. A save that makes several calls passes on the version each one returns. The CMS sends `ifVersion` with every edit of a screen and shows "This changed since you opened it" with a reload.
- **Labels (#184).** `src/labels.ts`. A screen's `labels` are `key=value` facts; every `Screen` view carries them and its `systemLabels` (orientation, kind, timezone, and locale when set: read-only, from its settings). `update_screen_labels` is a merge, like `add_group_members`, so it takes no `ifVersion` and leaves the screen's version alone: each key in `set` takes its value on every screen given (up to 1000), each in `remove` goes, the rest stay. A key is 1 to 63 characters, lowercase `a-z0-9`, with `-`, `_` and `.` between; a value 1 to 63 printable characters once trimmed, spaces allowed, stored as typed. The system keys, `name`, `id`, `status` and any `sf.` key are refused (`invalid_input`). A screen has at most 32 labels and an org's screens at most 100 keys between them: past either is `conflict`, checked from a read and again inside the batch, so two calls at once cannot pass it. `list_screens({ selector })` lists only the screens a selector matches (`@signforge/compiler/selector`; values case-insensitive, a missing key equals nothing, so `neq` and `notin` need the key; at most 10 terms; no `name`, `id` or `status`), before paging. `list_label_keys` counts each key's values, one value whatever its case, shown as most screens spell it, with the system labels marked `system`. A label change reaches no screen: smart groups will resolve selectors at publish (#186).
- **Group members.** `add_group_members` and `remove_group_members` change only the screens they name, so they cannot drop a screen someone else added; the CMS uses them. `set_group_members` replaces the whole list and should be given `ifVersion`.
- **Lists page.** Every `list_*` tool takes `limit` (default 50, at most 200) and `cursor`, and returns `next`. Pass `next` back as `cursor`, with the same filters, for the following page; `next` is `null` on the last page. A cursor is opaque. It holds the sort key of the last row returned, so rows added or removed between calls are neither repeated nor skipped. A cursor the server did not make is `invalid_input`. Most list tools read the org's whole list and cut the page (`page()`); `list_screen_status`, which the CMS polls, reads only its page in SQL (`keysetPage()`).
- **`update_screen_settings`.** Changes only the fields it is given. `null` clears `locale` (back to the player's default) or `displayHours` (always on). Display hours are checked by the contract's `displayHoursProblems`, the same check the player runs, so the CMS can show its messages as they are. A screen picks up a settings change with the next publish to it.
- **A screen's view** (`Screen` in every screen tool's output) adds what the CMS shows (`src/screen-state.ts`): `state` (`online`, `updating`, `asleep` with `wakesAt`, `unreachable`, or `needs_you` with a `reason`: `behind`, `revoked`, `nothing_published`, `fallback`), the last `heartbeat`, `showing` (what it should be showing now, worked out from its desired manifest with `player-core`: the playlist, whether a takeover plays it, its first spot, and an image hash for a thumbnail), and `displayOverride`. `status` is `revoked` once every credential the screen had is revoked (one that has not collected a credential yet is waiting, not revoked). A screen not heard from for the org's `unreachableAfterMinutes` (15 by default, `UNREACHABLE_AFTER_MS`) is unreachable; that is calm while it is on its desired manifest, because it keeps playing it, and `needs_you` / `behind` when it is not.
- **`list_screen_status`.** The fleet poll: each screen's `state`, `lastSeenAt` and manifests as `list_screens` gives them, and nothing else. It reads no settings and no manifests, and one page of screens in SQL over `(org_id, id)` (`screens.statusPage` in packages/db). For a page of `limit`, D1 reads `3 × (limit + 1)` rows for screens with one credential each (the screen, its credentials looked at twice for `revoked`, and one row past the page), plus the org's settings row once set: 10 rows for a page of 2, 64 for 20, whatever the org's size, and the same for a page after a cursor. A screen with revoked credentials, from a revoke or from pairing it again, reads about one more row for each. Through `/api/tools` the API also reads the member's row for the call (`requireOrg`). `list_screens` reads every screen and credential of the org on every page, and each uncached manifest. Measured in `test/screen-status.test.ts`.
- **`get_screen`.** Credentials come back without their hashes. `events` are the audit rows whose target is the screen, newest first, at most 20, each with the input the tool was given (secrets redacted).
- **`set_display_override`.** `on` or `off` lasts until the screen's next display-hours change, and at most 12 hours (`OVERRIDE_LIMIT_MS`, the only limit on a screen without display hours); `null` goes back to the hours. Stored on the screen (`display_override_json`), sent over the socket at once, and in every sync while the screen reports another override.
- **`identify_screen`, `restart_screen`.** Commands to a screen's socket (contract `DeviceCommand` `identify` and `restart`); a screen whose socket is down does not get them, and a revoked screen (every credential revoked) is refused with `conflict` (#180). They change nothing in the database, so they are marked `alwaysAudited`: audited, and their notices sent, though they stage no write.
- **`claim_screen`.** Pairs a screen (M3-08): `{ code, name, timezone, orientation, locale?, displayHours?, idempotencyKey? }` returns `{ screen }`. The code is as the screen shows it; case, spaces and dashes are ignored. An unknown, expired or already claimed code is `not_found`, one answer for all three. Every claim counts against the caller's rate limit (the `rateLimit` service, bucket `pairing_claim`: the API allows 10 a minute per member and per address) before the code is read, and over it is `rate_limited`; the tool needs `rateLimit`, so a caller without one is refused and no adapter can skip it. The screen collects its credential on its next poll. Two claims racing for one code: the second's batch fails and writes nothing (an error, not a refusal).
- **Brand kits.** Colours are hex. Leave out `onPrimary` or `onAccent` (or set it to `null` on update) to have it derived for 4.5:1 contrast; `derived` says which were. `warnings` lists pairs below 4.5:1; they do not stop a publish. Fonts are catalogue ids from `list_fonts` (`available: false` until the font's files are added; screens then draw with the template's font). A logo is a verified SVG or PNG image asset. The first kit becomes the default. A screen uses its own kit, else its groups', else the default: `reach` lists the screens a kit's edits will reach at the next publish, and `conflicts` the screens whose groups chose this kit and another (they cannot publish until the screen or a group is changed). Nothing reaches a screen until the next publish.
- **Spots.** Every spot tool works on the draft (packages/db, Drafts); a screen gets a spot only when a publish promotes it. A spot's view says whether it is `published` and whether its draft has changed since (`draftChanged`). `kind` is `template`, `image`, `video` or `url`, and each takes only its own fields: a template spot `templateVersionId` (fixed once made), `data` and `assets` (image fields to asset ids, each sent whole); an image or video spot a verified asset of that kind and a `fit`; a URL spot an https `url` (the contract's `safeUrl`). A template spot's data is checked as a screen would check it, with the compiler's `spotProblems` (the contract's `validateSpotData`, brand tokens and the template's duration range), and refused with `invalid_input`, one `details` entry per problem with `path` `data`, `bindings` or `durationMs`. An image field may stay empty in a draft until an asset is picked; the publish holds the draft back until then. A template spot's `bindings` (field name to `{ dataSourceId, path }`, sent whole; `{}` unbinds every field, and an edit without it keeps them) make those fields take their value from a data source, with the field's `data` as the fallback a screen shows without fresh data. Each source must be one of the org's (`not_found` otherwise; packages/db refuses another org's too), each field one the template can bind (not an image), each path a dot path (`daily.temperature_2m_max.0`), and for a news (`rss`), calendar (`ical`) or table (`csv`, `json-table`) source a path its normalised feed has (`items.0.title`, `events`, `rows.0.1`). A binding with `table` (the contract's `TableMapping`: `columns`, item property to column, and an optional `filter` `{ column, equals }` and `sort` `{ column, descending? }`), at path `rows`, fills a list field from a table source's rows, at most the field's `maxItems`; the contract refuses it on a field that is not a list, a property its items do not have, and a property without a default left without a column, and the tools refuse a source that is not a table and, once the source has a snapshot, a column it does not have (`binding for "items": menu has no column "Cost" (it has Item, Price)`). Before the first poll the columns are unknown; the poller then fails the source as `missing-column`. A template's manifest says which fields are live and their usual paths (`live`, docs/template-spec.md); the tools take any binding that passes these checks. `delete_spot` (#242) deletes the draft and its published version, and refuses with `conflict` while a playlist plays the spot in its draft or its published version, which screens may have (`org.spots.usedBy`, `details.playlists` with each one's id and name); its assets and data sources stay. With `ifVersion` it is refused (`conflict`) once the spot was saved past that version, at the read or, guarded in the batch as an edit is, before the commit; the spot editor's Delete and Try another template pass the version they hold. The playlist check guards drafts only at the commit: a publish that promotes a playlist naming the spot in the few milliseconds between the check and the delete's commit can leave that playlist's published version naming a deleted spot until the playlist is published again. The window is that short, so no guard is kept for it (review of #352). It goes through `packages/db`'s repository, so a spot made again with a deleted one's id continues its versions (`draft_tombstones`), and an edit read before the delete is refused. It is `people`: deleting is the person's choice, confirmed in the spot editor, so neither `/mcp` nor the drawer offers it.

- **`list_audit_log` (#82).** `src/audit.ts`. The org's audit rows (see The dispatcher, step 7), newest first, rows of one millisecond latest written first, one page read in SQL (`auditLog.page` in packages/db, over `audit_log_org_at_idx`, or `audit_log_org_target_idx` with a target). Every filter is optional and they combine: `actor.kind` (`user`, `agent`, `device`, `system`) and `actor.id`; `action` (a tool's name, a membership change such as `invite_member`, or `rate_limited`); `target.kind` and `target.id`, which need not name a row that still exists, so a deleted screen's history stays findable, and which find nothing for another org's ids; `from` (inclusive) and `to` (exclusive), in ms; and `query`, up to 100 characters found in the action, the actor's or target's id, or the recorded detail, ignoring ASCII case (`instr`, not `LIKE`, whose patterns D1 caps at 50 bytes). `detail` is the row's detail as written: `{ input }` for a tool, with `refused` for a refusal that changed something; the fields `membershipAudit` keeps for a membership change; `{ tool, refused }` for an agent's limit refusal. - **Alert channels (#88).** `src/alert-channels.ts`. Besides email, an org's alerts go to at most one Slack channel and one outgoing webhook, set by owners. Slack takes an incoming-webhook URL made in Slack for the channel (`https://hooks.slack.com/services/T…/B…/…`, the only form accepted). The webhook takes an https URL under the feed URLs' fetch-safety rules (no IP address, no port, no local name; the address it resolves to is checked at each send) and a signing secret of 32 to 128 characters of `A-Za-z0-9_-`, which the caller makes (the CMS: `whsec_` and 32 random bytes) so no tool output ever holds it; give either alone later to change it, a new secret rotating it. Each alert is queued as one delivery per channel (`alert_deliveries`) and sent by the API after the alert check (`apps/api/src/deliveries.ts`); a failure is retried 5 minutes later, doubling up to 2 hours apart, for 24 hours. `test_alert_channel` sends a `test` event now, tried once (email goes to the member asking; an agent cannot); `retry_alert_delivery` sends a pending or failed one now, one given up on getting one more try. `list_alert_deliveries` is the log, kept 7 days: status (`pending`, `delivered`, `failed`), attempts, the last HTTP status and error category, never the receiver's body.
  - **What a webhook receives.** A `POST` with `content-type: application/json` and the event as the body: `{ type, id, occurredAt, org: { id, name }, data }`. `type` is `screen.offline` (`data: { screen: { id, name, url }, lastSeenAt }`), `screen.back` (`data` adds `offlineSince`) `publish.finished` once every screen a publish switched plays it, was moved on by a later publish or was revoked, and at least one played it (`data: { publish: { id, revision, url, publishedAt }, screens, playing, replaced }`: of `screens`, `playing` say they play it, `replaced` were switched by a later publish before they did, and any other was revoked, so `playing + replaced` is never more than `screens`; `url` is its rollout in the CMS), `publish.requested` (M4-09) when someone asks to publish (`data: { request: { id, url, drafts, expiresAt }, by: { kind, id, name } }`: `drafts` how many it pins, `url` null until the approvals page (#115) gives a request one, `by.name` a member's name or an agent's client name where a page would show it, else null; never the request's reason, which is the asker's own text and read in SignForge), `agent.refused` (M4-08) when an agent is refused `forbidden` for the third time in a clock hour, at most once per grant and 5 times per org a clock hour (`data: { grant: { id, url, client: { id, name } }, refusals, tool, needs }`: `client.name` is null where a page would not show it (`shownClient`), `tool` and `needs` are the latest refused call's tool and the scope it needs, `url` the agent's page in the CMS), or `test` (`data: { message }`). `screen.url` is the screen's CMS page, null where the API has no `CMS_ORIGIN`. Times are ISO 8601. `id` is the same on every channel and every retry: drop one already seen. A 2xx answer is delivered; anything else, a redirect included (it is not followed), is retried.
  - **Checking the signature.** Headers `SignForge-Event-Id`, `SignForge-Timestamp` (Unix seconds when sent) and `SignForge-Signature: v1=<hex>`, the HMAC-SHA256 of `<timestamp>.<raw body>` whose key is the signing secret's whole text as UTF-8, `whsec_` included (unlike Svix-style secrets, nothing is base64-decoded). Compute it over the body as received, compare in constant time, and refuse a timestamp more than 5 minutes old, so a captured request cannot be replayed later.
  - **Slack.** The incoming webhook's message (docs.slack.dev, Sending messages using incoming webhooks and Formatting message text, as read 2026-11-18): `text` for the notification, and blocks with the screen (linked to its CMS page), its state, the org, and since when as a `<!date^…>` each reader sees in their own time zone. - **Schedule (M3-19).** `src/schedule.ts`. An entry aims a playlist at every screen (`target: 'org'`), a group (`groupId`) or one screen (`screenId`), on dates, weekdays and a daily window, each in the screen's own time zone (none: always). A screen plays the entry that applies with the highest `priority` (0 to 99), of equal ones the most specific target, then the later `startsAt` (so the newest of two takeovers), then the one published later (a manifest lists entries in publish order), else the default playlist: player-core's `resolvePlaylist`, which the screen runs. A takeover (`start_takeover`) is an entry with `startsAt` (default now) and `endsAt`, at most 24 hours apart and not already over, at priority 100; an entry with `endsAt` is a takeover, and a screen cuts in when the winning one changes. `update_schedule_entry` keeps an entry's kind: a schedule entry's priority and when, or a takeover's bounds (end it early, or extend it within a day of its start); `null` clears a schedule field. Deleting an entry never published removes it at once. Deleting a published one needs `content:publish` (the handler checks the caller's `scopes`) and only marks it (`deleted_at`, listed with `deleted: true`): screens keep the published version until a publish applies the deletion, either one of every change or one that pins it at the version returned, so it never rides along on someone else's pinned publish. `end_takeover` deletes a takeover and publishes that alone in one call. A takeover over for good (`ended`: its draft and published end both passed) is in no screen's manifest from the next publish, which deletes its row, pinned or not; `delete_playlist` deletes those of its playlist too. It runs `checkTemplateBundle` from the contract and refuses a failure with `invalid_input`, one `details` entry per problem, `path` naming the check (`manifest`, `forbidden-css`, `size`, `network`, `source-code`, `scripts`). - **Uploading an image.** The browser does the scaling with `@signforge/media`, and `uploadImage` there runs these steps:
  1. **`create_asset_upload`.** The input names each rendition (`landscape`, `portrait`) with its `sha256`, `type` (JPEG, PNG, WebP or SVG), `size` in bytes (at most 20 MB), and `width` and `height` as displayed (`null` for SVG). A raster rendition with no transparent pixel also has its `sample`, `{ sha256, size }`: a PNG of its darkest and lightest pixel per 16 px cell (`ManifestFile.sample` in the contract), which `@signforge/media` makes and a template reads instead of decoding the photo. An SVG has none.
     - A raster rendition must be no larger than the cover rule allows for its screen box (`imageSizeProblem` in the contract): at least one side within 1920x1080, or 1080x1920 for portrait. It must also decode to at most `MAX_IMAGE_PIXELS` (3840x2160, about 8.3 million pixels), so a 65,535x1,080 strip, which has a side in the box, is still refused.
     - It creates the asset as `pending`, with both renditions, in one write. For each file the org does not already hold, samples included, it returns `{ sha256, method: 'PUT', url, headers, expiresAt }`. The URL is an R2 presigned PUT to `up/<org>/<asset>/<sha256>` that lasts 15 minutes. It signs the content type and length, so R2 refuses any other.
  2. **PUT** each file to its `url` with the `headers` given. URLs that have expired (a retry with the same `idempotencyKey` returns the first call's) are renewed with **`renew_asset_upload`**, which signs new ones for the same pending asset's files not yet PUT.
  3. **`finalize_asset`.** It refuses with `conflict`, changing nothing, unless the asset has both renditions. It reads each file back from R2, re-hashes it, checks the size, reads the type and pixel size from the bytes (`readImageInfo`), and checks the screen box and pixel cap again. A sample is checked the same way, as a PNG of the size its rendition's sample has (`imageSampleSize`). Its pixels are not checked: that needs the rendition decoded, which a Worker cannot do, and a wrong sample misjudges only the uploading org's own text over its photo.
     - **All pass.** The files move to `o/<org>/b/<sha256>` and the asset becomes `verified`.
     - **Any fails.** Every upload for the asset is deleted, the asset becomes `rejected`, and the call is refused with `invalid_input`, one `details` entry per problem. That refusal is audited, because it changed the asset.
     - **A file not yet uploaded.** The call is refused and nothing changes.
     - **Called again on a verified asset.** It returns `changed: false`.
- **Uploading a video.** No transcoding: the file must already match the contract's `VIDEO_SPEC`. `uploadVideo` in `@signforge/media` checks it in the browser first (`@signforge/media-check`), then runs these steps:
  1. **`create_video_upload`.** The input is the file's `sha256`, `type` (`video/mp4`) and `size` (at most 500 MB). It creates the asset as `pending`, kind `video`, with no renditions: a screen of either orientation plays the one file. It starts an R2 multipart upload at `up/<org>/<asset>/<sha256>` and returns `{ uploadId, partBytes, parts, expiresAt }`: a presigned UploadPart URL for each 16 MiB part (the last is shorter), signed for its exact length, lasting an hour. `upload` is `null` when the org already holds the file.
  2. The browser PUTs each part and keeps the `ETag` header of each response. The bucket's CORS rule must expose `ETag`.
  3. **`finalize_video_upload`.** It takes `uploadId` and every part's ETag, parts 1 to N in order (it refuses a subset without changing anything, because R2 would complete one into a shorter file). It completes the upload, then reads the MP4 header over range reads and checks it (`checkVideo`), and re-hashes the whole file.
     - **All pass.** The file moves to `o/<org>/b/<sha256>` (R2 checks the hash again as it writes) and the asset becomes `verified`, with `width`, `height` and `durationMs` from the header.
     - **Any fails.** The upload is deleted, the asset becomes `rejected`, and the call is refused with `invalid_input`: one `details` entry per problem, `path` naming the check (`fps`, `profile`, `sha256`, ...), and the message ending with how to export a file that passes (`EXPORT_ADVICE`). Audited, as for images.
     - **Parts R2 cannot complete** (one missing, a wrong ETag), or nothing uploaded: refused, nothing changes; PUT again and retry.
  - `finalize_asset` and `renew_asset_upload` refuse a video, and `finalize_video_upload` an image, with `conflict`.
- **Assets.** An image asset's `sha256`, `type`, `size`, `width` and `height` are its landscape rendition's, and each rendition has its `sample` (`{ sha256, size }`, or `null` for SVG, an image with transparency or one uploaded before samples); a video's are its file's, and `durationMs` is its length (`null` for an image). `usageCount` and `spotIds` count spots that use the asset: image and video spots by `assetId`, template spots through their asset map. The tools are `people`: the dispatcher refuses an agent, a grant's or the in-CMS one, before anything is read, and `/mcp` does not list them, since an agent that managed grants could widen or keep its own. They need only `content:read`, so a viewer manages their own grants too. A change applies on the agent's next `/mcp` call, which reads the grant fresh; a revoke also deletes the provider's tokens (`stage.revoke`), so the next call gets 401. A grant's `client` is named as `/connect` names it (`shownClient`, `src/agent-clients.ts`): an unverified client's name only when plain, else `name: null` and its redirect's host. `revoke_agent_grant` is the action a membership ending writes too (apps/api, M4-04). `get_agent_grant_usage` (M4-08) reads the agents' calls over the last 7 days from the call log (the `agentCalls` service: Analytics Engine in apps/api): for one grant (`grantId`) or every one the caller may see, each grant's calls, changes, draft changes (changes by `content:draft` tools) and refusals (calls refused `forbidden` or `rate_limited`; not found, bad input and faults are calls, not refusals), zero for a grant with none, and for one grant its 20 most recent calls and its last refusal. The log failing in any way is `unavailable`. A call is its time, tool, `ok` or a refusal's code, whether the tool changes data, the scope it needs, and a change's target kind and id, as its audit row names them; never its input or output. A caller without the log is refused `forbidden`.
- **Connections** (#83; docs/backend-plan.md, Connectors). An account the org connected at a provider, which provider sources read through. `start_connection` is for people only: an agent (or any actor that is not a user) is refused with `forbidden`, since the callback finishes as the browser's session user and could never finish an agent's authorization. It stores an authorization (the SHA-256 of a fresh `state`, the PKCE verifier sealed by the `connectors` service, the member who started it, 10 minutes to live) and returns the provider's authorize URL, which alone holds the state. The provider sends the browser to the API's callback (`GET /api/connections/callback`), which runs `finish_connection` as the session's member: the state finds the authorization in that member's active org only and only if that member started it; anything else, an expired state or one finished before, is `not_found`. The authorization is deleted in the batch that stores the connection, and the batch fails unless that delete removed it, so a state makes at most one connection. Two finishes of one state at once (a browser sending the callback twice) can end either way: the provider grants its single-use code to one and refuses the other, and whichever commits first uses the state up; the other gets `not_found` (`refuseFailedCommit`). If the refused one wins, no connection is made and the person starts again; the grant the provider issued to the loser is revoked (`onDiscard`). A provider's refusal of the code is `invalid_input`; it still uses the authorization up (a state works once, refused or not), creates nothing, and is audited with the refusal and no target. With `connectionId`, the authorization reconnects that connection in place, keeping its id and its sources, and in the same batch makes those sources due at once with their failures cleared, so the backoff they built up while it needed reconnecting does not hold them back. The grant is sealed by the API, bound to the org and the connection's id; the view shows the provider, the account's name, the scopes granted, `status` (`active`, `needs_reconnect` once the provider refused the grant, `disconnected`), `expiresAt` and `lastError`, never a credential. `disconnect` revokes the grant at the provider where it can (a failure there is logged, and the credentials are deleted anyway), then deletes the connection, or, while sources read through it, keeps it as `disconnected` without credentials (`dataSourceIds` names them); disconnecting it again once they are gone deletes it. `oauthState`, `code` and `resource` are redacted in the audit log. Every connection tool needs the `connectors` service (`Connectors`), which the API builds from its provider adapters (apps/api/src/connectors).
- **Upload configuration.** `create_asset_upload`, `renew_asset_upload` and `create_video_upload` need the `uploads` service, an `UploadSigner` (`r2Presigner` in `src/upload.ts`). The API builds it from the Worker's settings (`apps/api/src/uploads.ts`); where they are not set it has none, and those tools are refused with `forbidden`.

Each tool's `description` is written for an agent choosing a tool, its `output` is the zod schema of what it returns, and its `example` is a valid input.

## Roles and scopes

- **Scopes.** They are `content:read`, `content:draft`, `content:publish`, `screens:manage` and `org:manage` (the org's settings).
- **Sessions.** A session holds every scope its role allows.
- **Agent grants (Milestone 4).** A grant names its own scopes, and they are capped by the user's role.

| Role | Scopes |
| --- | --- |
| owner | all |
| editor | all but `org:manage`; `content:publish` only while the org's `editorsPublish` is on |
| viewer | `content:read` |

Owner decision Q7 (can editors publish?), decided 2026-11-18: an owner chooses, per org (`editorsPublish` in the org's settings, on until changed). The dispatcher reads it on every call (`grantOf` in `src/dispatch.ts`), so a change applies from the next call. With it off, an editor keeps `content:read`, `content:draft` and `screens:manage`; an agent's grant is capped by the role in the same way, so an editor's agent cannot publish either. A publish refused for this reason is `forbidden` with the message "Only owners publish in this organization", and `GET /api/tools` leaves the publish tools out of the editor's list, so the CMS's command menu does not offer them. Separately, each tool sets a minimum role. Revoking a screen credential and changing the org's settings are for owners only. Members, roles and invitations are Better Auth's endpoints, not tools; its organization plugin lets only owners change them (`apps/api/src/auth/roles.ts`, tested in `apps/api/test/members.test.ts`).

## The dispatcher

`dispatch(registry, name, input, caller)` (`src/dispatch.ts`) runs these steps in order:

1. For an agent, counts the call against its grant's limits, and refuses it over one (see Agent limits).
2. Finds the tool.
3. Checks the role and scopes.
4. Validates the input.
5. For a keyed creation, returns the first result if the key was used before (see Idempotency keys above).
6. Refuses the call with `forbidden` if the caller lacks a service the tool `needs` (see Tool services), then runs the handler with `{ org: scoped(db, orgId), actor, role, scopes, input, blobs, services, write, notify, deliverNow, onDiscard }`.
   A handler reads through `ctx.org` but never writes: it stages each change with `ctx.write(org.<repo>.stage.<op>(...))`, which returns the row as it will be (see `packages/db`'s README).
   In tests it then parses the output with the tool's output schema and throws on a mismatch, before anything is written (`setOutputChecks(true)`, called by `test/setup.ts` here and in `apps/api`). Production skips the parse.
   A handler that did something outside the batch that must not outlive a failed call (`finish_connection`: a grant the provider issued) registers its undo with `ctx.onDiscard(undo)`. The dispatcher runs every undo, best effort and logged, when the call does not succeed: a refusal, an error, or a commit that failed.
   A handler that changes something a screen should hear of at once queues it with `ctx.notify((screens) => screens.manifest(...) | screens.revoked(...) | screens.command(...))`. The notices go out after step 7, only if the commit succeeded, through the caller's `notify` service (`ScreenNotifier`; the API's reaches each screen's Durable Object). `ctx.deliverNow(id)` queues an alert delivery the same way, sent through the caller's `deliverNow`. A notice that fails is logged, not returned: the screen catches up at its next sync.
7. Commits the staged writes in one D1 `batch()`, together with an `audit_log` row and, for a keyed creation, its idempotency record. The batch is atomic: if the audit row cannot be written, the change is not made either, and the request fails. The audit row holds:
   - actor kind and id;
   - client id (`cms`, `sf-push`, or an agent's OAuth client);
   - action (the tool name);
   - target;
   - `detail_json` holding the input, with secret-looking fields redacted (`redact()`).

A call that staged nothing changed nothing, and writes nothing: no audit row either (publishing the current manifest again, revoking a revoked credential). The exception is a tool marked `alwaysAudited`, whose effect is a command to a screen (`identify_screen`, `restart_screen`): every call of it that is not refused is audited (a refused one, such as a command to a revoked screen, sent nothing). This is deliberate (decided 2026-11-17): the audit log answers "what changed, and who changed it"; an agent retrying a call, or a person publishing twice, would otherwise fill it with rows that describe nothing. Reads are not audited. A refusal (`ToolError`) or any other error discards what was staged, except a refusal that changed something on the way: a handler marks one with `new ToolError(code, message, details, true)`, and what it staged is committed, audited with `refused: { error, message }` in its detail. So far `finalize_asset` does this, when it rejects an upload, and `finish_connection`, when the provider refuses the code (it uses the authorization up). Such a refusal has no output, so the tool names its target from the input, or has none (`target` may return undefined). If its batch fails (what it staged was changed first by another call), it is answered as a failed commit of a change is: a guard's conflict, or the tool's `refuseFailedCommit`. Files in R2 are not part of the batch: `finalize_asset` moves or deletes uploads before its batch, so a failed batch can leave a verified file in place (harmless; finalize finds it again) or a rejected upload deleted with its asset still pending (finalize then reports it not uploaded).

### Tool services

What a tool may use beyond its input and the org's data (GLOSSARY.md) is one object, `caller.services` (`ToolServices` in `src/tool.ts`, every field optional): `uploads`, `feedUrls`, `alertSecrets`, `places`, `tables`, `templateCheck`, `connectors`, `members`, `rateLimit`, `agentCalls` (M4-08: the org's agent call log, read by `get_agent_grant_usage`), and the two the dispatcher uses itself after the commit, `notify` and `deliverNow`. A tool lists those its handler uses in `needs` (`needs: ['rateLimit', 'places']`), and its handler sees exactly those, each there, as `ctx.services`; the dispatcher passes the caller's object through as it is. A call whose caller lacks one is refused before the handler runs, the same for every tool: `forbidden`, `<tool> needs <the service in words>, and this caller has none` (`SERVICE_WORDS`). A need is per tool, not per call: `update_data_source` needs `feedUrls` though only a new URL is sealed, and `register_template_version` needs `templateCheck` and `rateLimit` in the platform registry too.

Each environment builds them with one constructor: the API's `toolServices` (`apps/api/src/tool-services.ts`), which `/api/tools` takes whole and `/admin` takes only the parts of it needs; `/mcp` (M4-06) takes all of them but `members`; tests use `fakeServices` (`test/services.ts`). A new service is a field in `ToolServices` with its words in `SERVICE_WORDS`, a line in the API's constructor and one in `fakeServices` (the compiler asks for each), and `needs` on the tools that use it.

### Agent limits

Each agent grant (`actor.kind === 'agent'`, counted by `actor.id`, its grant id) may make 120 tool calls a minute, and 30 changes a minute and 2,000 a UTC day (`AGENT_LIMITS` in `src/tool.ts`; owner decision on #39, constants rather than settings). A change is a call to a tool that `mutates`, counted when it is made, even if it is refused later or changes nothing; reads count only as calls. People are not counted. The windows are fixed, the minute and the UTC day, by the counter's clock when the call reaches it.

The call is counted before anything else, even before the name is looked up (a name that is no tool counts as a call): over a limit it is refused with `rate_limited`, a message naming the limit and when it resets, and `details: { limit, retryAfterSeconds }` (`limit` is `calls_per_minute`, `writes_per_minute` or `writes_per_day`). The grant is not read, the handler does not run, nothing is written, and an idempotency key is left unused, so a retry after `retryAfterSeconds` works. A call refused by a write limit still counts as a call; one refused by the call limit counts for nothing, and a refused write is not counted as a write. Each window, the minute or the UTC day, gets one audit row for the calls refused in it, whichever limit refused them: action `rate_limited`, no target, and `{ tool, refused: { error, message, details } }` in its detail, from the first refused call (`tool` is the name the agent called). So the log shows a grant hitting its limits once per minute or day, not once per retry. The row's id is made from the org, the grant and the window (`auditLog.appendOnce` in `packages/db`), so calls racing to write it write one, and the counter is told it is written (`AgentLimiter.audited`) only once it is: if the write fails, the call is still refused, the failure is logged, and the window's next refused call writes it.

The adapter passes the counter as `caller.agentLimiter` (`AgentLimiter`); an agent caller without one throws, so no adapter can skip it. The API's (`apps/api/src/agents/grant-object.ts`, `agentLimiter(env)`, #107) counts in two places. Calls go to the `AGENT_CALL_LIMIT` rate limit binding, keyed by grant id. It counts per Cloudflare location (owner decision on #107), so an agent whose calls land in several locations gets 120 a minute in each, and a read costs no Durable Object request and writes nothing. Writes go to one Durable Object per grant: one count for every location, which the daily budget needs. The minute's and the day's writes are stored with every counted write, so they survive the object hibernating, being evicted or redeployed, and nothing keeps the object awake between writes. A call the binding refuses is told to retry at the end of the Worker's minute; the binding's own minute is not aligned with it, so the wait is approximate. Once an isolate has recorded a minute's call-limit refusal, its later refusals in that minute ask for no row. Milestone 4: `tools/list` (`describeTools`) does not go through `dispatch`, so the MCP adapter must count it itself if it should count.

### The platform registry

`platformRegistry` holds `register_template_version` and `set_template_version_status` again, dispatched with `platform(db)` (from `@signforge/db`) instead of an org's scope, so they write base templates. Its changes are audited in `platform_audit_log`, because they belong to no org. Only `/admin` uses it. It is never served on `/api`, so no org member can change a base template. A tool works on both scopes when it is declared with `defineSharedTool` and reaches data only through what both scopes share (`templates`, `auditLog`, `commit`, `orgId`, which is null on the platform's).

Callers so far:

- `/api/tools`: actor `user` with the session's user id, client `cms`, and every service: a `rateLimit` keyed by user and by address (`pairing_claim` on the `PAIR_CLAIM_LIMIT` binding, `place_search` on `PLACE_SEARCH_LIMIT`, `table_read` on `TABLE_READ_LIMIT`, and `page_read` on `PAGE_READ_LIMIT`, which the agent's fill counts for each link it reads, #314), `places`, Open-Meteo's geocoding, and the rest.
- `/api/tools` also passes `publishLock` (the org's Durable Object), and its `notify` service's `manifests` queues a publish's screens 50 a message (`apps/api/src/publish.ts`).
- `/admin`'s manifest upload: actor `system` with id `sf-push`, role owner, scope `content:publish` only, and only the `notify` service.
- `/admin`'s template registration (`sf template push`): actor `system` with id `sf-push`, role owner, scopes `content:draft` and `content:publish`; the platform registry for base templates, the org registry for an org's.
- Both `/api/tools` and `/admin`'s template registration (which has only these two services) pass `templateCheck`, through the API's `TEMPLATE_CHECK` service binding (`apps/api/src/template-check.ts`, which parses the report with the contract's `parseTemplateRuntimeReport`), and a `rateLimit` that counts `template_check` per org on `TEMPLATE_CHECK_LIMIT`.

## Publishing: drafts and the loader

`src/publishing.ts` is what the publish tool (`src/publish.ts`) builds on. Spots, playlists and schedule entries each have a draft (the row) and a published version (see `packages/db`'s README); edits change the draft only.

- `loadOrg(org)` reads everything a publish needs: the org's settings, with its publish revision, first, then the rest in one round of parallel queries. Reading the revision before any content is what lets the publish order guard cover all of it, and playlist versions before their items what lets each playlist's guard cover its items.
- `promoteDrafts(org, graph, opts)` checks each draft that differs from its published version, in order: spots, then playlists (every item must be a published spot), then schedule entries (their playlist must be published). A draft is checked by compiling a probe screen that plays it (`probeDrafts`: the draft-to-spot module's `compileProbe` in `@signforge/compiler/draft`, reading the org graph through `graphReads`), for each orientation the org's screens have, in the org's time zone for new screens (UTC without one), so its problems are exactly the ones a screen would get. The CMS's stage compiles the same probe, and `apps/cms/test/registry/draft-to-spot.test.ts` holds the two to the same spot. A spot may use only an approved template version, or keep a retired one it was already published with. A draft that passes is staged for publishing; one that fails keeps its published version, if any, and is reported in `held`. It never blocks the rest.
- `compileInputFor(graph, screenId)` and `loadCompileInput(org, screenId)` give a screen's published graph as `compileScreen` takes it: image files are the asset's rendition for the screen's orientation, a video is the asset's own file, a template bundle's size comes from its stored check report.
- `publishOrg(org, { hash, now }, pins?)` promotes drafts and compiles every screen. With `pins` (`{ kind, id, version }[]`), only those drafts are promoted, and a pinned draft that changed or was deleted since is refused with `conflict` (`{ id, version }`, the version now, 0 if gone): a publish of what a person saw (the editors) or approved (Milestone 4's publish requests) leaves everyone else's drafts alone. A screen that cannot compile is reported with its problems and keeps its manifest; the others publish. With no default playlist set, no screen can. It stages writes and returns them; the caller commits them in one batch with its publish row (`publishes.stage.insert`), its rollout rows (`publishes.stage.addScreens`) and its switch of each screen's desired manifest (`screens.stage.setDesiredManifest`). The writes start with the publish's place in the org's order (`publishes.stage.advance`, from the revision `loadOrg` read), and each promotion is guarded by its draft's version. So if another publish committed after this one read, or a draft it promotes was edited since, the batch fails with `StaleVersionError` (the dispatcher's `conflict`) and nothing is written or switched: an older publish never replaces newer content on a screen. Load and compile again to retry.

`test/publishing.test.ts` checks that the loader and compiler produce `sf build`'s manifest for `examples/stress` (its golden).

### The publish tools (M3-18)

- **`publish`** (`content:publish`, editor; refused to editors when only owners publish, Q7): `drafts` pins what to publish, or without it every changed draft is. It runs `publishOrg`, stores each changed screen's manifest in R2 (`o/<org>/m/<screen>/<id>.json`, before the commit, so a screen told of it can fetch it), then stages in the call's one batch `publishOrg`'s writes, the publish row (`revision`: the org's publish revision it moves to, the "v15" people see), its rollout rows and each changed screen's switch. A screen whose manifest is unchanged is not touched, and with nothing promoted and no screen changed nothing is written (`publish: null`, no audit row). The switched screens are told after the commit with one `screens.manifests(rows)` notice. The same batch deletes the weather sources the spot editor made (`madeBySpotEditor`, ids from the CMS's `weatherSource`) that nothing binds: not a draft, not a published version once it commits, and not a published version as it read them, which an Undo sends screens back to, so a source the publish unbinds goes at the next one. A source made in the last 15 minutes is kept, since the editor binds a new one in an autosave a moment later. `dataSources.stage.deleteUnbound` checks the age and the bindings again in its statement, so a spot bound to one meanwhile keeps it. The editor's own delete is refused while a published version still binds the source (#98). It returns what was promoted, what was held and why, the schedule entries it deleted (`removed`), each screen's outcome (`updated`, `unchanged`, `failed`), the sources removed, and the publish made with the one before it (`previousId`, for Undo). With no default playlist, a publish whose newly live regular schedule entries on every screen at all hours all play one published playlist makes it the default in the same batch (a takeover or a narrower entry never does; its screens get nothing, as the answer says), guarded by the settings' version it read, and says so in `madeDefault` (`{ id, name }`, #243). Its audit row records it under `detail` (`auditDetail`: a tool's way of adding to its row what its input does not name, redacted as the input is and never over `input` or `refused`). `list_audit_log` with `action: 'set_default_playlist'` finds those publishes too.
- **`roll_back_publish`** `{ publishId, ifLatest? }`: each screen goes back to the manifest it had right after that publish (`publishes.asOf(revision)`), with nothing compiled, as a new publish (`restoresId`). Drafts and published versions are not changed, so the next publish sends the current published content again. An undo passes the publish it undoes as `ifLatest` and is refused `conflict` (`{ latestId }`) once a later publish exists, which it would take back too. A roll back further than the publish before can reach a manifest whose data source or asset was deleted since.
- **`list_publishes`** (newest first, paged by revision) and **`get_publish`** (one, or the latest): who, when, and the rollout: screens switched, how many say they play it, how many a later publish switched before they said so (a screen still saying it plays this one counts as playing, never both), how many it still waits on (`open`: neither playing, replaced nor revoked; its rollout is over at 0, which is when the CMS's publish page says complete), once finished how many the five-minute check saw playing it (`reached`: 0 when it was replaced before any check saw a screen report it, which includes one played and replaced between two checks), and per screen `playing`, `waiting`, `downloading` (`filesMissing`), `asleep` (`wakesAt`), `offline` (`lastSeenAt`), `fell_back`, `revoked` or `replaced`, from the screen's state (`src/screen-state.ts`). One module decides all of it, for these tools and the five-minute check: `src/rollout.ts` (the rollout outcome), from the facts `packages/db` reads (does the screen report the publish's manifest, is it still its desired one, is it revoked).
- **Publish requests** (M4-09, `src/publish-requests.ts`): how anyone without `content:publish` publishes, an agent or an editor where only owners publish.
  - **`request_publish`** (`content:draft`, editor; a write, so it counts against an agent's write limit; keyed by `idempotencyKey`) pins drafts as `{ kind, id, version }`, 1 to 100, each once, each refused `conflict` (details `{ id, version }`, 0 for one that is not there, or not this org's) unless it is at that version now, with a `reason` for approvers: one line, 1 to 500 characters, no control characters, shown as the asker's words. It waits 7 days (`expiresAt`), then is `expired`. The same batch queues `publish.requested` (Alert channels, below).
  - **`list_publish_requests`** (newest first, paged; `pending: true` keeps those not decided and not expired) and **`get_publish_request`**, at viewer: how an agent learns the outcome. A request is `pending`, `approved` (with `publishId`, the publish it made, null when that changed no screen), `declined` or `expired`, with who asked (`requestedBy`: a user, or an agent grant and its client), the pins and the reason.
  - **`approve_publish_request`** (`content:publish`, editor, so capped by `editorsPublish`; `people`, so no agent, with `content:publish` or without, nor the CMS's own agent, decides) publishes exactly the pinned drafts at the pinned versions as the approver, through `publish`'s own path with `drafts` (`runPublish`), and marks the request approved in the same batch, guarded by its version, so of two decisions one commits and the other is `conflict`. A pinned draft changed since is `conflict` with `{ id, version }` and nothing is written: the request stays pending. Other drafts are never published by it. Its audit row is the approver's, targets the request, and names who asked and the publish it made (`detail: { requestedBy, publishId }`), so the request's row, the approval's and the publish link through the request's id. **`decline_publish_request`** (the same scope, role and `people`) marks it declined. A request already decided or expired is `conflict` with `{ status }`.
- **`set_default_playlist`** (`content:publish`, so editors may not where only owners publish): what every screen plays when no schedule entry says otherwise. It has no draft and takes effect at the next publish, whatever that publish pins. No screen can be published to without one. Playlist views say `isDefault`.

The API's five-minute check marks a rollout finished once every screen it switched plays it, moved on or was revoked (`findUnfinishedRollouts` reads the unfinished publishes and their facts through the partial index `publishes_unfinished_idx`; `tally` in `src/rollout.ts` decides), and sends `publish_finished` unless the check saw no screen play it (email, and Slack and the webhook if its rule says) in the same batch as the mark (`finishRollouts`, `publishes.finish`), so it goes once. The publish tools set `publishes` on their definition, so the dispatcher runs them one call at a time per org (`Caller.publishLock`: the API's org Durable Object) and, when a commit loses a race (`StaleVersionError`: another publish, an edit of a draft it promotes, or a screen deleted since the read, which `publishes.stage.addScreens`'s guard checks), runs the handler again from a fresh read, up to 3 times, then answers `conflict`. `test/publish-scale.test.ts` publishes a 1,000-screen org through counting bindings: 14 D1 queries (one batch of 1,051 statements: D1 counts a batch as one query), 1,000 R2 writes and one notice, under the Free plan's 50 queries but over its 1,000 calls to Cloudflare services per invocation; Paid allows 10,000.

## Adding a tool

1. Write it with `defineTool` next to its kind (`src/screens.ts`, `src/groups.ts`, …).
   - Name it in snake_case.
   - Write the description for an agent.
   - Give it the narrowest scope and role.
   - Set `mutates: true` if it changes anything.
   - Give a `target` for the audit log.
   - Give an `output` schema: what it returns, as zod, written in `src/outputs.ts` under the tool's name and given as `output: outputs.<name>`. The handler's return type is checked against it at compile time, and every output against it in tests. `src/outputs.ts` imports only zod, the contract, the compiler's types and (through `src/screen-state.ts`) player-core, all of which the CMS's DOM typecheck can load, as the CMS types its calls from it (`@signforge/tools/outputs`, types only); never import a tool file or a Workers type there. A schema the input shares goes there too.
   - A `list_*` tool pages: spread `pageInput` (`src/paging.ts`) into its input, add `next: nextOutput` (`src/outputs.ts`) to its output, and cut the rows with `page()`.
   - Give an `example`.
   - Name in `needs` the tool services its handler uses (see Tool services), and read them from `ctx.services`. Do not check for them yourself: the dispatcher refuses a call without one.
2. Name id fields after their kind, such as `screenId` or `playlistIds`.
3. Reach data only through `ctx.org`, and write only by staging: `ctx.write(ctx.org.<repo>.stage.<op>(...))`. A creating tool sets `idempotent: true` and adds `idempotencyKey` (`src/fields.ts`) to its input. A missing row is `throw notFound(...)`, and a repository's `NotInOrgError` maps to `not_found` on its own.
4. An update tool (one that changes a row a person or agent edits: named `update_<thing>` or `rename_<thing>`, or `set_<thing>_members` for one that replaces a list) is conditional:
   - Give the row a version: a `row_version` column (`rowVersion()` in `packages/db/src/schema.ts`, with a migration). The repositories move it on with every `stage.update` and `stage.touch`.
   - Put `version` (`src/fields.ts`) in the row's view, set from `row.rowVersion`.
   - Add `ifVersion` (`src/fields.ts`) to the input, and pass it to the repository: `ctx.write(org.<repo>.stage.update(row, patch, input.ifVersion))`. For a change to what belongs to a row (a group's members), `stage.touch(row, input.ifVersion)` moves the row's version on, guarded the same way.
   - That is all. The repository refuses a stale version before staging, and again inside the batch; the dispatcher turns either into `conflict` with `{ id, version }`. The tool does not compare versions itself.
   - A tool that replaces a whole list also gets add and remove forms (`add_group_members`, `remove_group_members`), which need no version.
5. Add it to `TOOLS` in `src/registry.ts`.

`test/isolation.test.ts` then calls it as org B's owner once for each id field in its input schema, optional ones and those of one branch included: org A's id in that field, org B's own rows in the rest. It expects `not_found` naming A's id. A tool with no id fields must succeed without returning anything of org A's. The audit log is the exception, since it repeats what org B's own calls in the test were given, org A's ids among them: `list_audit_log` must list exactly org B's own rows (`LISTS_CALLS`). An id field of a new kind fails that test until you map it in `ORG_IDS`; a field it cannot reach with a valid input fails until the tool's example reaches it, or, for a field only another kind of spot has, until `REACHED_BY` gives the input that does.

## Tests

- `test/isolation.test.ts`: generated from the registry, as above.
- `test/conventions.test.ts`: fails on a tool without an output schema or whose output is not its entry in `src/outputs.ts`, a `list_*` tool without paging, or an update tool without `ifVersion` in its input and `version` in its output (`update_screen_labels`, a merge, needs none), and checks the output check and paging itself.
- `test/versions.test.ts`: a stale `ifVersion` is refused and writes nothing, even when the change lands between the read and the commit; group members added and removed without dropping anyone's.
- `test/labels.test.ts`: `update_screen_labels`'s merge, every key, value and count limit, the reserved keys, `list_screens({ selector })` matching case-insensitively and on system labels, `list_label_keys`, `claim_screen`'s labels, and another org's screens refused.
- `test/write-guard.test.ts`: generated from the registry. It runs every tool that changes data on a D1 that records any write sent outside `batch()`, and any writing batch other than the dispatcher's commit (one run while the handler runs, or one that does not end with the audit row), and fails if there is one. A tool whose example refuses before writing is set up to get further in `PREPARE`.
- `test/screen-status.test.ts`: `list_screen_status` gives the states `list_screens` does, reads no manifest, and reads one page's rows from D1 (counted from D1's own `rows_read`) however many screens the org has.
- `test/members.test.ts`: who may call each member tool, what an agent may do, and that a change asks Better Auth (faked) only about a row of the caller's org. With real Better Auth, apps/api's `test/member-tools.test.ts`.
- `test/audit.test.ts`: `list_audit_log` pages newest first without repeating or skipping rows of one millisecond, lists an agent-limit row, filters, searches with 100 characters, returns and searches redacted inputs as redacted, gives an invitee's email to owners only, and refuses another org's cursor.
- `test/dispatch.test.ts`: role and scope checks, validation, the audit log and redaction, a failing audit row rolling the change back, and idempotency keys.
- `test/connections.test.ts`: the connection tools with the API's OAuth stubbed: a state finishes once, for its member and org, within its time; reconnect in place; disconnect; provider data sources; no state, code or grant in an output or the audit log.
- `test/tools.test.ts`, `test/templates.test.ts`, `test/assets.test.ts`, `test/videos.test.ts`: what each tool does. The video tests upload media-check's ffmpeg-made clips, passed in by `vitest.config.ts`.

They run in workerd against local D1, with `packages/db`'s migrations applied, and local R2.

`test/e2e/upload.test.ts` runs in Node (`vitest.e2e.config.ts`), as part of `pnpm test`. It drives Chromium (Playwright's, or `SF_CHROMIUM`) and a Miniflare Worker (`test/harness-worker.ts`). That Worker runs the dispatcher and serves the bucket's S3 API, which checks presigned signatures. The test:

- uploads a 4K photo with an EXIF rotation through `@signforge/media` and these tools;
- forges an upload, which is refused and removed;
- sends PUTs of the wrong size, type or key, which R2 refuses;
- uploads a video in two presigned parts through `uploadVideo`, has a 60 fps video refused in the browser before any call, and has the same video, PUT past the browser check, rejected by `finalize_video_upload`;
- tries to delete an asset in use, which is refused.
