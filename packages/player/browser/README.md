# Player browser tests

The player and the template SDK tested where they can break: in headless Chromium, through Playwright, run by Vitest. `pnpm test` at the root runs them with everything else; `pnpm --filter @signforge/player test` runs only the player's.

Chromium, not the Pi: these tests check behaviour, not frame rates. Performance still needs a Pi measurement (`device/pi/isolate.py`).

## First run

The tests use Playwright's Chromium. If it is missing:

```sh
pnpm --filter @signforge/player exec playwright install chromium
```

## What runs

- `global-setup.ts` builds the player with Vite into a temporary directory (never `dist/player`) and bundles `fixtures/template.ts` with the real SDK into one HTML file. Every run tests the current source.
- `fixture-server.ts` serves the built player at `/`, content at `/content/` (manifest, blobs, data snapshots, all in memory), and a supervisor at `/supervisor/` that holds a credential and the API base it is bound to (`supervisorCredential` and `supervisorApi`, `FIXTURE_CREDENTIAL` and the server's own `deviceApi` at first; `token`, `credential` GET, POST and DELETE, the `alive` beat, and `display/on` and `display/off` POST, as `device/pi/supervisor.py` answers them) and answers 404 to everything else. A test can:
  - `publish(content)`: serve a new manifest; the player sees it at its next poll. A manifest poll whose `If-None-Match` names the current id gets a 304, as the API does.
  - `serveLastGood(content)`: serve that content's files too, as the API serves a screen's last good manifest.
  - `intercept(/path regex/, { status })`, `intercept(/path regex/, 'stall')` or `intercept(/path regex/, { bytesPerSecond })`: fail a path, send the headers and half the body and then nothing, or send the body slowly. Returns a function that removes the rule.
  - `setData(id, snapshot)`: serve a data source snapshot.
  - play the API's sync: `POST /content/sync` answers as the API does. `syncs` holds every request; play counts are stored per epoch as the API stores them (a repeated seq adds nothing) and summed by `storedCounts()`; `serverOffsetMs` makes the server time that far from the real time; `nextSyncS` sets the interval; snapshots set with `setData` are sent when newer than the screen holds; `commands` are sent once; `loseCountReplies` processes that many syncs carrying counts and drops their answers.
  - play the API's socket: `/content/ws` accepts a WebSocket and answers `ping` with `pong`. `push(msg)` sends a socket message, `dropSockets()` drops them, `socketMessages` holds what the player sent, `openSockets`/`socketsOpened` count them. Content is served with CORS, so `content=${server.localUrl}/content` puts it on another origin, as the API is: only then does the player sync and open a socket.
  - play pairing: requests to the API origin (`localUrl`) need a bearer credential in `authorised` (401 otherwise). `POST /content/pair/start` hands out a code (`pairings`; `pairingTtlMs` sets how long it lasts), `POST /content/pair/poll` answers waiting, expired or paired; `claim(code)` claims one and returns its credential, `revoke(credential)` refuses it and sends `revoked` on the sockets. Set `supervisorCredential = undefined` for a freshly flashed screen. Each request record has the `bearer` it carried.
  - read `requests` / `requestsTo(regex)`: every request, its status, its `If-None-Match`, and `abortedAt` if the client gave up on it.
- `content.ts` builds a manifest in memory (`edit` changes it before its id is computed: schedule, playlists, display hours). Every spot uses the fixture template; its `mode` field picks the behaviour: `ok`, `throw` (throws in `prepare`), `hang` (never ready), or a hostile mode that tries to reach the spot's `target` URL (see `fixtures/template.ts`). The template shows `label` and lists the titles of `items` (a list of up to 3 rows of `title`), trusting the shape as a news template would, so `items: {}` throws. A spot may set `items` and `bindings`; each bound source is added to the manifest's data sources. A bound spot waits up to 3 s for its feeds before prepare, so a feed that never answers holds it in that wait. A spot can also carry its own file (`asset`, passed to the template as asset `file`). A spot with `video` (bytes, e.g. `fixtures/clip.webm`: Playwright's Chromium has no H.264) is a video spot instead, and one with `url` a URL spot. `buildContent(h.brandTemplateHtml, spots, { brand })` gives the screen a brand kit (fonts and logo as bytes); `h.brandTemplateHtml` is the same script in markup that uses every brand token, the brand fonts and `$brand.logo`, each with a fallback (`BRAND_FALLBACKS` in `global-setup.ts`). See `brand.test.ts`.
- `global-setup.ts` also builds the player with `CMS_ORIGIN=http://cms.test` (provided as `cmsOrigin`), so a page on that made-up host may drive the preview. Playwright's routing answers `cms.test` and `evil.test`; the browser runs with Chromium's local network access checks off so those pages can frame the player on 127.0.0.1.
- `harness.ts` gives each test file one browser (`useHarness({ siteIsolation: true })` runs it with `--site-per-process`, as Chromium on the Pi isolates sites by default and the headless shell does not; `containment.test.ts` does) and each test a fresh context (empty Cache Storage, no service worker until the player registers one) and fixture server. `openPlayer` opens the player with `?poll=1` (with `clockAt`, on Playwright's clock from that instant) (pass `query` as a function of the server to build options from its URLs); `until(predicate)` waits on `window.__sf`; `onScreen()` reads the label, the listed item titles and the play flag of the template drawn on top. `playerServer()` starts a fixture server alone, for a page to frame the player. Templates sit inside a wrapper frame (see Template containment in `docs/architecture.md`), so `page.frames()` lists two frames per template.

Testing-only query options the tests use: `?poll=<s>`, `?stall=<s>` (the download stall timeout, 30 s by default), `?spots=` and `?transition=` (`cut`, `crossfade`, `fade`, `fade<ms>` or `<ms>`; see `src/main.ts`).

## Adding a test

Put it in the file for its area, or a new `browser/<area>.test.ts`. Start with `const h = useHarness();` at the top of the file, then:

```ts
const content = h.content([{ id: 'a', durationMs: 600 }, { id: 'b', mode: 'throw' }]);
const p = await h.openPlayer((server) => server.publish(content), { stall: '1' });
const s = await p.until((s) => s.log.length >= 2);
expect(spotsPlayed(s)).toEqual(['a', 'a']);
```

Keep spots short (500 to 1000 ms) and wait on state, never on fixed sleeps. Break the behaviour by hand once and check the test fails.
